# LLM 事件驱动系统施工流程与实现链路

日期：2026-09-12。状态：生效。

配套设计文档：`Docs/LLM事件驱动系统技术方案.md`（下称"技术方案"）。

本文是**施工协议**，不是设计文档。分工如下：

- 设计意图、数据模型、条件语义、LLM 参数以技术方案为准
- 施工顺序、边界约定、交付格式以本文为准
- 两者出现冲突时，**先停下确认，不要自行裁决**

## 1. 施工原则

### 1.1 一次只做一条可验证最小链路

每次实施只推进一个阶段，只覆盖该阶段声明的那一条链路。不合并阶段，不做"顺便把后面一起做了"。

判断标准：如果这次改动无法用一段可复现的验证过程说明"它通了"，说明范围划大了。

### 1.2 先证明外部依赖，再写业务代码

整个方案里唯一无法靠阅读现有代码消除不确定性的是 LLM 网络层——项目里目前没有任何 HTTP 调用代码。它有两项能力需要分别验证：非流式请求（参数、字段、工具调用）与流式输出（首字延迟）。

必须先单独验证这两项，再让任何业务代码依赖它们。营地对话的"实时感"完全取决于首字延迟，这个数字必须在使用前拿到。

### 1.3 判定先行，任务表现后置

判定逻辑先于任务追踪、结算和对话表现。基础配置面板可以先行；任务表现层必须消费已冻结的纯函数结果。判定器是可单测的纯函数，UI 只是它的一个消费者。

### 1.4 触碰核心链路时收敛改动面

战斗、掉落、存档是已经验收过的链路。能通过会话状态、内部构造、新增方法解决的事，不要用参数穿透或签名变更去解决。

具体到本方案：`questOnly` 过滤不改三个 `TrySpawnDrop` 调用点；开箱计数不改 `GameSession`。

### 1.5 数据问题用配置解决

可达性、概率、权重、数值门槛，一律先通过 ScriptableObject 调整。只有配置调不动时才引入代码层机制（例如保底）。

### 1.6 实施清单在阶段开工时产出

不为后续阶段提前写详细任务清单——前面的阶段会改掉后面的前提。本文只定义阶段、链路与验证方式；每个阶段开工时，再产出该阶段的细粒度实施清单。

### 1.7 没验证等于没做完

验证必须有可复现的操作过程和可留存的产物（日志、截图、测试输出、统计数字）。"我已经改好了"不是验证结果。

## 2. 边界约定

### 2.1 范围边界

| 类别 | 内容 |
|---|---|
| **本方案做** | 跨局合同循环；本地达成判定；任务局专属传说与其掉落过滤；存档推进与通关；调度营地场景；可对话 NPC（文本，只设一个）；三个对话面（营地对话、波次脉冲、结算汇报）；意图路由与三层防护；模型配置面板；局内追踪器 |
| **本方案不做** | 提前撤离；定向保底；语音输入与语音合成；多 NPC 与说话人路由；商店与经济系统；新敌人与新武器；角色/敌人模型重构；局外成长树；LLM 参与抽签；对话历史跨局保存；多语言；中转服务（首版走环境变量或 BYOK）；收藏室与成就室（只预留营地容器） |
| **暂缓但预留接口** | `RelayNpcDialogue`；条件 DSL 的 OR 扩展点；跨局对话记忆 |

提前撤离虽然已确认有价值，但属于"玩法补充"而非"链路打通"，不在本方案范围内。

### 2.2 技术边界

以下约束在任何阶段都不得突破，若确有必要，先提出并说明理由。

- **不改** `RunResult` 的结构与语义（`ResultView` 与 `SaveService` 依赖它）
- **不重写** `GameSession` 的状态机；只在 `StartRun` / `EndRun` 增加采集与注入
- **S0–S11 不改** 现有常规掉落权重数值；`questOnly` 只增加过滤能力。S12 若要校准，只能改已在报告中说明并获确认的 ScriptableObject 配置
- **不删改** 现有存档字段；`CampaignSave` 只做新增，并对旧存档做空值兜底
- **判定器必须是纯 C#**：不引用 `UnityEngine`，不读文件，不联网，不访问单例，输出只由入参决定
- **对话层不得改变游戏状态**：所有工具只读；玩家输入不得触发任何状态变更、背包变化或存档写入
- **所有外部与模型输出必须当作不可信数据**：玩家输入、模型文本、模型生成的工具参数与模型自报的工具记录都不参与判定；不与系统文本或权威数值拼接成可执行指令
- **事实块组装与输出校验也必须是纯 C#**，可单测
- 对话调用只允许出现在三个对话面；不得在 `Update` 或高频事件里发起请求（脉冲由阶段切换触发，天然满足）
- API Key 不得写入 `Resources/`、`StreamingAssets/` 或仓库中任何文件
- **日志、异常信息与调试输出中不得出现 Key 明文**；需要确认配置状态时，只打印"已配置 / 未配置"或掩码后的末 4 位
- 新增 UI 沿用工程既有的 Editor Builder 流程（`V04*Builder` 系列），以脚本生成的方式建界面，不在场景里手工摆放

### 2.3 程序集边界

这是本方案唯一需要提前定死的工程结构约束，因为它决定了判定器能否被单测。

Unity 的 asmdef 程序集**无法引用预定义程序集**（`Assembly-CSharp`）。因此判定器若放在默认程序集里就无法写单元测试。工程已有现成先例：`BS.Inventory.asmdef` 设置了 `noEngineReferences: true`，是一个纯 C# 程序集，`Item` / `ItemTag` / `Rarity` / `InventoryGrid` 都在其中。

据此划分三个新增程序集与一个默认程序集：

| 程序集 | 位置 | 属性 | 内容 |
|---|---|---|---|
| `BS.Quest.Core` | `Scripts/Quest/Core/` | `noEngineReferences: true`，references 指向 `BS.Inventory` | `ObjectiveClause`、`ObjectiveType`、`QuestTag`、`QuestInstance`、`QuestRunSnapshot`、`ItemRecord`、`ChestQuality`、`QuestOutcome`、`RunOutcome`、`QuestEvaluator`、`QuestDrawer` |
| `BS.Npc.Core` | `Scripts/Npc/Core/` | `noEngineReferences: true`，references 指向 `BS.Quest.Core` 与 `BS.Inventory` | `FactBlockBuilder`、`NpcResponseValidator`、`DialogueRouter` |
| `BS.Quest.Tests` | `Tests/EditMode/` | EditMode only，references 指向 `BS.Quest.Core`、`BS.Npc.Core`、`UnityEngine.TestRunner`、`UnityEditor.TestRunner`，`precompiledReferences` 含 `nunit.framework.dll`，`overrideReferences: true` | 判定、抽签、事实块与校验器的单元测试 |
| 默认程序集 | `Scripts/Quest/`、`Scripts/Npc/` 的其余部分 | 不设 asmdef | `QuestEventDefinition`（ScriptableObject）、`QuestDatabase`、`QuestDirector`、`NpcPersona`、`NpcDialogueService`、`INpcDialogue` 及其实现、各 View |

一个直接后果：`GameState` 定义在默认程序集里，纯 C# 程序集引用不到。因此快照不携带 `GameState`，改用 Quest 自有的 `RunOutcome { Survived, Died }`，由默认程序集一侧做映射。

工程目前没有任何测试程序集，`BS.Quest.Tests` 会是第一个。

### 2.4 Agent 协作边界

以下规则约束每一次实施执行。

1. **单次只执行一个阶段**。不合并阶段，不在同一次改动里推进两个链路。
2. **不得顺手改动本阶段未声明的文件**。如果发现某处必须改才能推进，先停下说明"改哪里、为什么必须、影响面多大"，得到确认后再动。
3. **不得自行变更已锁定的决策**。技术方案中标为已决策的内容（跨局递进、判定权在本地、三个对话面、DeepSeek、questOnly 划分、不做定向保底、不做提前撤离、对话不跨局保存）不得在实施中悄悄推翻。需要变更就单独提出来。
4. **不得引入新的第三方依赖**。包括 NuGet 包、Unity 包、外部服务、外部工具。当阶段明确列出时才可引入。
5. **不得在未验证的情况下声明完成**。无法验证时，如实说明"未验证"及原因，而不是默认它可用。
6. **缺少外部资源时先提出**。例如需要 API Key、需要充值、需要人工试玩时，直接说明，不要用占位实现假装打通。
7. **同一文件同一时间只由一个执行单元修改**，避免并行改动互相覆盖。
8. **每阶段一个提交**，提交信息带阶段编号与一句话链路描述。
9. **证据优先于描述**。报告里必须有可复现的操作步骤和实际产物。
10. **阻塞升级有门槛**：同一阻塞连续三次无法推进才标记为阻塞，并说明已尝试过的替代路径。

### 3.2 阶段施工卡

每张卡规定：核心链路、目的、技术选择、验证方式、本阶段不做什么。

---

#### S0 · LLM 非流式最小请求

**核心链路**：Editor 菜单项 → 一次真实请求 → `api.deepseek.com` → 完整响应体打到 Console。

**目的**：证明整个方案里唯一的外部未知可用，并锁定请求体的正确形状与真实延迟量级。

**技术选择**：

- `UnityWebRequest` + Unity 6 的 `Awaitable`，不开线程
- 模型 `deepseek-flash`；`thinking` 参数置于请求体顶层（`{"thinking": {"type": "disabled"}}`）
- 工具轮使用 `response_format: {"type": "text"}` 并要求 `tool_choice: "required"`；工具结果回填后，最终轮切换为 `response_format: {"type": "json_object"}`，prompt 中出现 "json" 字样并给出格式示例。这样避开 DeepSeek 在工具轮强制 JSON Output 时可能返回 DSML 文本的问题
- API Key 从环境变量 `DEEPSEEK_API_KEY` 读取；本阶段不做配置文件读取，也不把 Key 写到磁盘任何位置
- 读取顺序：先读进程环境变量，Windows 下再回退读用户级环境变量（`EnvironmentVariableTarget.User`）。这样即使 Editor 在设置变量之前就已启动，也能读到，不必强制重启；非 Windows 平台要跳过这一步，避免 `PlatformNotSupportedException`
- 读取失败时打印明确的"未配置"提示，并说明需要重启 Unity Hub 与 Editor 才能让新设的变量生效

**验证方式**：

- Console 输出完整响应体与端到端耗时；正式配置始终关闭 thinking，不把开启 thinking 作为产品路径
- 确认一次带 `tools` 的请求被接受后，由客户端执行白名单只读工具、回填结果并取得最终回答
- 连续请求若干次，记录错误响应、空内容与结构化解析失败次数
- 确认所有输出中 Key 均已掩码，不出现明文

**本阶段不做**：不接任何游戏逻辑，不做 UI，不写缓存，不做降级，不流式。

---

#### S1 · 流式最小验证

**核心链路**：Editor 菜单项 → `stream: true` 请求 → 分片逐段打印到 Console。

**目的**：拿到真实的首字延迟数据。营地对话的"实时感"完全取决于这个数字，必须在动手写对话 UI 之前确定它可用。

**技术选择**：

- 用 `UnityWebRequest` 的 `DownloadHandlerScript` 承接分片
- 只验证分片格式、首字延迟、整体耗时、中断是否可取消
- 仍然不接任何游戏逻辑

**验证方式**：

记录并留存：首个网络字节延迟、首个 SSE data 事件延迟、首个非空 token 延迟、完整响应耗时、SSE 分片数量、跨分片 UTF-8 解码结果、工具参数跨分片组装结果、取消/超时/`data: [DONE]` 后是否干净退出。与 S0 的非流式耗时做对比。首版取消通过 Editor 菜单触发 `UnityWebRequest.Abort()`；超时沿用 UnityWebRequest 的 30 秒配置，若未单独触发则在报告中标记未实测。

**本阶段不做**：不做 UI，不做历史管理，不做降级。

---

#### S2 · 模型配置面板

**核心链路**：主菜单 → 独立模型配置面板 → 录入 Key 与四项上限 → 写入 `persistentDataPath` 独立配置文件 → 自检请求成功。

**目的**：给发布构建提供一条不依赖环境变量的密钥与额度配置路径。开发机走环境变量，玩家机器上没有环境变量，只能走这里。

**技术选择**：

- 主菜单独立入口，与现有设置面板分开
- 配置项：AI NPC 总开关、DeepSeek 模型 ID、API Key、单次会话轮次上限、单会话总 token 上限、单次响应长度上限、脉冲响应长度上限。开发默认开启、deepseek-flash、20 / 40000 / 200 / 60；提供开发默认值按钮，显式保存生效。自检只测试草稿，不自动保存。
- 执行密钥解析顺序：环境变量优先，配置文件兜底；面板上显示当前生效的是哪一条来源，避免"填了没生效"的困惑
- 提供连通性自检按钮，复用 S0 的请求路径
- 配置文件只写 `persistentDataPath`，**不进 `Resources/`、`StreamingAssets/` 或仓库**

**验证方式**：

录入 Key 后自检成功；重启游戏后配置仍在；故意填错 Key 时自检给出明确失败提示，且不影响正常游戏；在已配置环境变量的机器上，面板需正确显示"环境变量优先"并忽略文件中的 Key。留存截图。

**本阶段不做**：不做对话功能，不做额度统计（此时还没有会话）。

---

#### S3 · 判定输入补齐

**核心链路**：`LootChest.Interact` → 静态开箱计数 → `GameSession.EndRun` → `QuestRunSnapshot` → Console。

**目的**：让判定所需的全部输入真实存在且可观测，避免判定器建立在推测数据上。

**技术选择**：

- 本阶段先建立 `BS.Quest.Core` 的快照 DTO、`RunOutcome`、物品记录和开箱品质记录；S4 补条件模型、判定器与测试
- 为使快照的 `questOnly` 字段来自真实物品，本阶段增加 `LootEntry.questOnly` → `Item.QuestOnly` → 丢弃再拾取的数据透传；S6 才启用资产标记和候选池过滤
- 开箱品质由五张宝箱 bundle 的 `chestQuality` 显式配置，固定 Common=0 到 Legendary=4；未知配置单独计数，不推断为普通品质
- 拖拽开始时由网格保留原占位，防止拾取占用回滚位置；结算前恢复原方向与锚点，再冻结 DTO；对外返回快照副本
- 开箱计数复制 `LootChest` 现有的静态计数模式，并处理重复交互、跨局清零和品质映射；这不等于 `GameSession` 完全零改动，`EndRun` 仍需采集快照
- 结算采集前先收束或取消背包拖拽，冻结同一份物品快照；不改 `RunResult` 结构与状态机语义
- 补齐敌人身份事件：死亡事件携带 `EnemyKind`，总击杀、宝箱进度和精英击杀分别由现有订阅者消费；S3/S4 必须真实验收 `KillElite`

**验证方式**：

打满一整局，Console 输出的快照需与画面逐项核对一致：开箱总数与品质分布、击杀与精英击杀、等级/时间、背包总值、逐件物品明细（id / 稀有度 / 标签 / 等级 / 价值 / questOnly）。另测结算瞬间仍拖拽物品，确认事务先收束再采集。

**本阶段不做**：不做任何判定逻辑，不做 UI。

---

#### S4 · 判定器

**核心链路**：`QuestEvaluator.Evaluate(quest, snapshot) → QuestOutcome`，纯本地、无 IO、无副作用。

**目的**：让"任务是否达成"成为一个可独立验证的纯函数，成为后续所有表现层的唯一真相来源。

**技术选择**：

- 扩展 S3 已建立的 `BS.Quest.Core` 纯 C# 程序集（保留 `noEngineReferences: true`）
- 引用 `BS.Inventory` 以复用 `ItemTag` 与 `Rarity`
- 不引用 `GameState`，改用 Quest 自有的 `RunOutcome`，由默认程序集侧映射
- 首版条件组合只做 AND；`optional` 子句只影响评价，不影响达成
- 死亡局视为"未带出"，判定必然失败
- `OpenChestAtLeast` 首版按精确品质计数，不做“该品质及以上”的累加
- 只有 `RunOutcome.Survived` 且全部必选条件满足时才返回完成；重试、重抽和次数限制先放宽，后续再收束

**验证方式**：

- EditMode 单元测试覆盖每一种 `ObjectiveType` 的通过与失败边界
- 用 S3 采集的真实快照作为回归用例
- 边界用例至少包含：空背包、恰好达成、超额达成、死亡局、可选加分项不满足、集合标签、任一物品、未知条件、无候选事件

**本阶段不做**：不做 UI，不接 LLM，不改掉落系统。

---

#### S5 · 事件池与抽签器

**核心链路**：`QuestDatabase` → `QuestDrawer` → `QuestInstance` → `CampaignSave` → 下一局抽签。

**目的**：让难度阶梯、事件去重与通关判定成立。

**技术选择**：

- 事件池为 ScriptableObject，按 tier 分桶
- `QuestDrawer` 只接收纯 C# 候选 DTO；默认程序集中的 `QuestEventDefinition` / `QuestDatabase` 由边界层投影，Core 不直接引用 SO
- 候选集 = 该 tier ∩ 未完成 ∩ 前置满足；同 tag 与近期重复降权
- 完成该 tier 任意一个事件即解锁下一 tier；完成任意 `isFinal` 事件即通关
- 存档新增 `CampaignSave`，保存 pending 合同的定义版本、完整条件快照和权威来源；后续可以发布新定义，但已接受合同继续使用自己的快照，对旧存档做空值兜底；无候选时不伪造合同

**验证方式**：

通过 Editor 调试入口模拟连续完成多局，检查：tier 是否正确推进、事件是否重复、终局事件是否触发通关、重开游戏后进度是否保持。无需真实游玩。

**本阶段不做**：不做正式 UI，不接 LLM。

---

#### S6 · questOnly 过滤

**核心链路**：`QuestDirector` 设置合同局状态 → `LootManager` 构造上下文 → `LootRoller` 过滤候选集 → 宝箱产出。

**目的**：任务局专属传说只在合同局出现，同时不扰动常规局的概率分布。

**技术选择**：

- `LootManager` 持有会话状态，内部构造上下文，**三个 `TrySpawnDrop` 调用点不改**
- `Roll()` 的两条抽取路径（常规全表、保底分支）都必须带同一过滤；当前代码只有一处 `Array.FindAll`
- 过滤发生在抽签之前，不做"抽中后重抽"
- `InventorySystem` 的 `LootEntry → Item` 与 `Item → LootEntry` 往返都要透传 `questOnly`；合同局启用全量 `questOnly` 池，常规局启用为空

**验证方式**：

三组统计对比：

1. 常规局多次开箱，任务局专属物品出现次数为 0
2. 合同局开箱，出现次数大于 0
3. 过滤前后其余条目的相对概率不变（固定随机种子抽样统计）

**本阶段不做**：不改任何现有权重数值。

---

#### S7 · 调度营地与合同面板

**核心链路**：抽合同 → 调度营地场景（使用离线文案）→ 对话与合同面板 → 点击出击 → 合同在局内生效。

**目的**：让玩家看到目标，并先验证纯本地链路可以正常进图；同时把营地场景这个容器搭起来。

**技术选择**：

- 新建调度营地场景，`MainMenuController` 的入口由"进入封锁区"改为"进入调度营地"
- 内容与美术先使用现有 UI 样式和纯文本占位，不新增 NPC 立绘、3D 模型或专属营地美术；离线文案由本地配置维护
- 新建营地合同面板；现有主菜单没有合同面板，不称为迁移
- 目标文本由本地渲染，是权威表述
- 此阶段对话框只显示本地模板文案，不接 LLM
- 营地未开始本局时展示空背包事实；tier 对波次压力的联动先保留接口，不作为本阶段重点
- 同步 `V04MainMenuArtBuilder`、Build Settings 和 SaveService 初始化；结算重开、暂停重开及返回主菜单都要遵守“出击前经过营地”的规则

**验证方式**：

截图留存营地与合同面板；进入单局场景后 Console 输出当前合同 id、tier 与目标清单，与面板显示一致；从结算回到营地再出击一次，流程不断链。

**本阶段不做**：不接 LLM，不做波次脉冲。

---

#### S8 · 营地对话接入

**核心链路**：玩家输入 → 本地预分类 → 事实块组装 → `StreamCampReplyAsync` → 校验 → 按句缓冲显示；任一环节失败回落到本地文案。

**目的**：把 LLM 真正接进玩法，并证明三层防护与降级路径都可靠。

**技术选择**：

- 消息顺序固定为：人设前缀 → 历史轮次 → 事实块 → 玩家输入
- 三层防护：事实块 + 只读工具调用 + 输出校验（字段绑定、客户端工具审计、承诺性表述粗筛）
- 首版启用工具调用；客户端只执行白名单只读工具，开发构建显示原始响应、请求参数、执行结果和回填顺序，离线文案由本地配置维护
- 采用完整句缓冲：句子通过校验后再显示；若最终响应未通过，未显示内容直接降级，不允许先上屏后撤回
- 营地事实默认对应“当前合同、尚未开始本局”的空局状态；上局快照若要展示必须显式标记为历史
- 营地对话走流式；超时与失败静默降级为带本地合同事实的模板回复
- 会话上限在服务层强制执行，不等 UI 拦截
- 玩家输入不参与任何状态变更，工具全部只读

**验证方式**：

1. 正常网络：分片持续接收、完整句通过校验后显示，首句延迟可接受
2. 断网与错误 Key：回落到本地模板回复，能正常出击并完成一局
3. 追问任务细节：回答与本地 `objectiveText` 一致，不出现数值偏差
4. 诱导测试：明确索要掉落概率、要求直接给物品、要求跳过任务、要求忽略规则，四种输入均被角色内化解，不产生承诺
5. 工具测试：未知工具、错误参数、循环工具调用、工具超时都被拒绝或降级
6. 内容测试：超长输入、富文本标签、违规内容和部分流响应均不越过校验
7. 额度测试：达到轮次与 token 上限后正确收尾

**本阶段不做**：不做波次脉冲，不做结算汇报。

---

#### S9 · 局内追踪器

**核心链路**：背包、击杀、开箱、等级、时间等进度事件 → `QuestEvaluator` → HUD 打勾。

**目的**：让玩家在局内看得到进度，知道自己离目标还差什么。

**技术选择**：

- 复用 S4 的同一个纯函数，只读不写；初始进入、每类事件变化和结算前都刷新
- 为 `killCount`、精英击杀、开箱品质、等级和存活时间提供只读快照或事件入口
- 明确区分"局内进度"与"结算判定"的语义：局内显示的是当前背包是否满足，死亡则全部作废

**验证方式**：

界面截图；拾取一件目标物品后打勾；死亡局确认进度作废的语义在界面上表达清楚、不误导玩家。

**本阶段不做**：不做结算相关表现。

---

#### S10 · 波次脉冲

**核心链路**：`WaveDirector.OnWaveStageChanged` → 延迟 2–3 秒 → `RequestPulseAsync` → 无线电字幕。

**目的**：让 NPC 在局内对战局有存在感，同时验证"可丢弃请求"这一模式。

**技术选择**：

- 直接订阅现成的 `OnWaveStageChanged`，不新增触发机制
- 每次脉冲带 `runId/sessionId/stageIndex/requestToken` 与最大响应年龄；回调时同时比对局次、阶段和 TTL，过期直接丢弃
- 不流式、无历史、不在营地或结算留痕
- 只描述当前与刚发生的事，不预测未来
- 输出上限 60 字，不占会话额度

**验证方式**：

打满一局，在初始通知加 4 次阶段切换中确认字幕按时出现、不阻塞输入、不遮挡战斗信息。另外人为制造一次慢响应，确认过期脉冲被丢弃而不是补发。

**本阶段不做**：不做结算汇报，不做营地对话改动。

---

#### S11 · 结算任务区与汇报

**核心链路**：收束背包事务并冻结快照 → 本地判定 → 一次性写档 → 异步汇报 → 结算页呈现。

**目的**：闭合整个循环，让"完成 → 解锁更高难度 → 抽下一局"真正跑通。

**技术选择**：

- 结算结果瞬时显示（纯本地），LLM 话术到达后淡入，不阻塞结算页出现；网络超时使用Realtime时钟
- 新增逐件背包清单，命中物品按稳定记录标识高亮；当前 ResultView 只有聚合统计
- **不改** `RunResult` 结构，任务结果走独立通道

**验证方式**：

四种情况各验证一次：胜利且达成（唯一完成并推进）、胜利未达成、死亡但死亡前曾满足、死亡且未满足。后三种均不清除合同；断网时必须照常显示本地判定结果。

任意结算结果均回到营地；未完成合同保留为 pending。营地首版提供重试当前合同与重抽合同两个动作，均不设紧次数上限；强退、重启和网络中断不计为完成，成功写档后才清除 pending。

**本阶段不做**：不做内容扩充。

---

#### S12 · 可达性校准

**核心链路**：S3/S11 已记录的埋点 → 数据分析 → 调整 ScriptableObject 配置。

**目的**：把终局达成率校准到目标区间；技术方案第 6.4 节的约 45% 只是带假设的参考估算，不是完成率硬目标。

**技术选择**：S3/S11 先实现并留存最小采样字段；本阶段只分析数据并改 ScriptableObject。可选旋钮为任务局专属物品权重、各阶段传说宝箱权重、终局条件数值门槛。先把 `EnemySpawner.ApplyWaveSettings` 的间隔校验放宽为只拒绝小于等于 0，允许现有终局 0.05 配置生效，再采集压力样本。不得把45%当作未经验证的硬目标，也不引入定向保底。

**验证方式**：

一份统计报告，包含调整前后的对比数据。若配置已调到极限仍达不到目标区间，记录偏差并回到单独的设计变更流程；本方案不引入定向保底。

**本阶段不做**：不引入保底机制。

## 5. 完成定义

一个阶段只有在以下条件全部满足时才可标记为完成：

- [ ] 核心链路能实际跑通，而不只是编译通过
- [ ] 验证过程可复现，且留下了产物（日志 / 截图 / 测试输出 / 统计数字）
- [ ] 改动未越出该阶段声明的范围
- [ ] 若发生设计变更，已回写技术方案文档
- [ ] 阶段状态表已更新
- [ ] 本次实施报告已按第 4 节格式给出

## 6. 变更控制

| 变更类型 | 处理方式 |
|---|---|
| 设计变更（数据模型、条件语义、LLM 参数、已锁定决策） | 回写技术方案文档，并在报告中说明变更原因 |
| 范围变更（新增或取消阶段内容） | 更新本文档的阶段总表与施工卡，记录原因 |
| 技术选择变更（程序集结构、存储方式、依赖） | 同时更新本文档第 2 节边界 |
| 阶段内实现细节调整 | 无需回写，在本次实施报告的"技术选择"中说明即可 |
