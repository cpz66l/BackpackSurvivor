# 第21课 · 构筑最小兑现

> 日期：2026-07-31  
> 目标：把第14课的 DualWield 从“邻接检测 + UI 高亮”推进为“真实影响战斗的背包构筑收益”。

---

## 一、这节课实现了什么

第21课完成了 Demo 冲刺期最关键的一步：**背包摆法开始真实改变战斗实体**。

本课之前，双手枪左右相邻时，背包 UI 能显示金色接口，但战斗层并不知道这条邻接效果。玩家看到的是“像是触发了”，实际收益还没有兑现。

本课之后：

- `AdjacencyRuleBook` 成为邻接规则事实源，UI 和战斗都读取同一套规则。
- `AdjacencyEffectResolver` 成为有效效果解析器，负责把候选邻接效果筛成真实生效效果。
- `BackpackWeaponActivator` 在基础武器上限之外，额外消费真实 `DualWield` 效果。
- 两把手枪左右相邻时，默认 1 把自动武器上限可以临时突破到 2 把。
- 三把手枪横排时，只允许一组 `DualWield` 生效，避免“三持”。
- `InventoryUIController` 的金色接口显示改为读取真实有效效果，避免 UI 承诺和战斗兑现错位。

本课完成后，背包系统从“能放东西”进一步进入“摆法影响战斗”的阶段，这是《背包幸存者》核心玩法成立的关键节点。

## 二、最终代码（关键片段）

### 1. 邻接规则事实源：AdjacencyRuleBook

`AdjacencyRuleBook` 放在 `BS.Inventory`，保持纯 C#，不依赖 Unity。

```csharp
public static class AdjacencyRuleBook
{
    public static IReadOnlyList<AdjacencyRule> Rules => rules;

    private static readonly List<AdjacencyRule> rules = new List<AdjacencyRule>
    {
        new AdjacencyRule(
            ItemTag.Pistol,
            ConnectableSides.Right,
            ItemTag.Pistol,
            ConnectableSides.Left,
            AdjacencyEffectId.DualWield),

        new AdjacencyRule(
            ItemTag.Pistol,
            ConnectableSides.Left,
            ItemTag.Pistol,
            ConnectableSides.Right,
            AdjacencyEffectId.DualWield)
    };
}
```

这里的重点不是规则有多复杂，而是**规则从 UI 中被拔出来了**。  
UI、战斗、后续数值系统都只能读取同一份规则，避免“表现一套、结算一套”。

### 2. 有效效果解析器：AdjacencyEffectResolver

```csharp
public static List<AdjacencyEffect> ResolveValidEffects(List<AdjacencyEffect> candidateEffects)
{
    List<AdjacencyEffect> validEffects = new List<AdjacencyEffect>();

    if (candidateEffects == null) return validEffects;

    AddValidDualWieldEffects(candidateEffects, validEffects);
    // 当前真实结算只开放 DualWield；可堆叠效果在接入真实收益时再加入解析分支。

    return validEffects;
}
```

`ResolveValidEffects()` 的职责是把 `InventoryGrid.ScanAdjacency()` 扫出的候选效果，变成真正允许生效的效果。

### 3. DualWield 防三持

```csharp
private static void AddValidDualWieldEffects(
    List<AdjacencyEffect> candidateEffects,
    List<AdjacencyEffect> validEffects)
{
    HashSet<Item> usedItems = new HashSet<Item>();

    foreach (AdjacencyEffect effect in candidateEffects)
    {
        if (effect == null) continue;
        if (effect.EffectId != AdjacencyEffectId.DualWield) continue;

        if (usedItems.Contains(effect.ItemA)) continue;
        if (usedItems.Contains(effect.ItemB)) continue;

        validEffects.Add(effect);
        usedItems.Add(effect.ItemA);
        usedItems.Add(effect.ItemB);
    }
}
```

这一段只处理 `DualWield`，不再把“一个 Item 参与过效果”当成全局规则。  
为什么？因为未来同一个物品可以同时参与多种效果，比如一把手枪既双持，又吃攻速芯片。互斥规则应该按效果类型处理，而不是按物品全局处理。

当前版本暂时只开放 `DualWield` 真实结算，因此先只写双持解析；`AddStackableEffects()` 留到第22课接入基础芯片时补。

### 4. BackpackWeaponActivator 拆出激活入口

```csharp
private bool TryActivateItem(Item item)
{
    if (item == null) return false;
    if (activeWeaponItems.Contains(item)) return false;

    foreach (WeaponSlot weapon in weaponSlots)
    {
        if (weapon == null) continue;
        if (weapon.WeaponObject == null) continue;
        if (weapon.WeaponObject.activeSelf) continue;
        if (weapon.Tag != item.Tag) continue;

        weapon.WeaponObject.SetActive(true);
        activeWeaponItems.Add(item);
        return true;
    }

    return false;
}
```

`TryActivateItem()` 是本课的小核心。  
基础激活和双持额外激活都走同一个入口，保证“激活场景武器对象”和“记录背包物品已激活”不会分裂成两份逻辑。

这里必须检查 `weapon.WeaponObject.activeSelf`，否则两个手枪物品可能都标记为激活，但实际复用了同一个场景武器对象。

### 5. 基础激活 + 双持额外激活

```csharp
private void RefreshActiveWeapons()
{
    List<AdjacencyEffect> effects = inventorySystem.Grid.ScanAdjacency(AdjacencyRuleBook.Rules);
    List<AdjacencyEffect> validDualWieldEffects = AdjacencyEffectResolver.ResolveValidEffects(effects);

    DeactivateAllWeapons();

    List<Item> items = inventorySystem.Grid.GetUniqueItems();
    int activatedCount = 0;

    foreach (Item item in items)
    {
        if (activatedCount >= activeWeaponLimit) break;

        if (TryActivateItem(item))
            activatedCount++;
    }

    ActivateDualWieldWeapons(validDualWieldEffects);
}
```

顺序很关键：

1. 先扫描并解析有效邻接效果。
2. 再清空旧激活状态。
3. 按背包位置优先级激活基础武器。
4. 最后根据有效 `DualWield` 追加激活邻接武器。

这样可以保证 `DualWield` 是“基础激活武器的邻接奖励”，而不是免费绕过背包优先级。

### 6. 双持奖励激活

```csharp
private void ActivateDualWieldWeapons(List<AdjacencyEffect> validDualWieldEffects)
{
    if (validDualWieldEffects == null) return;

    foreach (AdjacencyEffect effect in validDualWieldEffects)
    {
        if (effect == null) continue;
        if (effect.EffectId != AdjacencyEffectId.DualWield) continue;

        bool itemAActive = activeWeaponItems.Contains(effect.ItemA);
        bool itemBActive = activeWeaponItems.Contains(effect.ItemB);

        if (itemAActive && !itemBActive)
            TryActivateItem(effect.ItemB);
        else if (itemBActive && !itemAActive)
            TryActivateItem(effect.ItemA);
    }
}
```

这里刻意不处理“两把都没激活”的情况。  
原因是：`DualWield` 是激活武器的邻接奖励，不是凭空激活任意一组武器。如果两把手枪都放在背包右下角，且没有吃到基础激活位，它们不应该绕过左上优先级。

### 7. UI 改为显示真实有效效果

```csharp
List<AdjacencyEffect> candidateEffects = grid.ScanAdjacency(AdjacencyRuleBook.Rules);
List<AdjacencyEffect> validEffects = AdjacencyEffectResolver.ResolveValidEffects(candidateEffects);

ConnectableSides visibleSides = item.GetWorldConnectableSides();
ConnectableSides activeSides = GetActiveSides(item, validEffects);
itemView.SetConnectors(visibleSides, activeSides);
```

本课修正了一个重要表现问题：  
三把手枪横排时，候选效果可能有两组，但真实效果只允许一组。如果 UI 仍显示候选效果，玩家会看到“两个方向都金色”，但战斗只兑现一组。

现在 UI 金色接口来自 `validEffects`，也就是**真实生效效果**。  
灰色接口仍表示“这个方向可以连接”，金色接口才表示“这次真的触发了效果”。

## 三、周期链路

本课完成后的邻接链路：

```text
背包内容变化
    ↓
InventoryGrid.OnChanged
    ↓
BackpackWeaponActivator.RefreshActiveWeapons()
    ↓
InventoryGrid.ScanAdjacency(AdjacencyRuleBook.Rules)
    ↓
AdjacencyEffectResolver.ResolveValidEffects()
    ↓
基础武器按 GetUniqueItems() 位置优先级激活
    ↓
DualWield 对基础激活武器追加邻接武器
    ↓
activeWeaponItems 记录真实激活的 Item
    ↓
InventoryUIController.Redraw()
    ↓
UI 显示激活角标 + 真实有效接口金色高亮
```

本课的核心闭环是：

```text
规则表决定候选
解析器决定真实生效
战斗层消费真实效果
UI 层展示真实效果
```

这个闭环解决了两个常见问题：

- UI 显示触发，但战斗没有收益。
- 战斗实际生效，但玩家看不出来为什么。

## 四、设计思考

### 1. 为什么不直接把 activeWeaponLimit 改成 2

如果只是把 `activeWeaponLimit` 从 1 改成 2，那么两把武器是否激活只取决于数量，不取决于摆法。  
玩家不会感到“我通过背包布局赚到了收益”。

本课选择让 `DualWield` 突破默认上限，是因为它把收益和玩家操作绑定起来：

```text
两把手枪存在 ≠ 双持
两把手枪左右正确相邻 = 双持
```

这就是背包构筑游戏最重要的反馈：摆法不是装饰，摆法有战斗价值。

### 2. 为什么 DualWield 必须依附基础激活位

如果双持可以免费激活任意一组相邻手枪，那么玩家把两把手枪放在背包右下角也能触发。  
这会破坏第15课建立的“背包位置决定优先级”。

所以本课规定：

```text
基础激活位先决定一把武器
DualWield 只能给这把已激活武器的邻接伙伴追加激活
```

这让背包位置优先级和邻接构筑同时成立。

### 3. 为什么三把手枪不能三持

三把手枪横排：

```text
A - B - C
```

候选上可能同时出现 `A-B` 和 `B-C`。  
如果两组都生效，中间的 B 就同时参与两组双持，效果会变成“三持”或连锁激活。

当前 Demo 设计里，`DualWield` 是“一组两把武器”的特殊构筑，不是连锁武器网络。因此 resolver 用 `usedItems` 保证每个 Item 最多参与一组 `DualWield`。

### 4. 为什么有效效果解析器不该全局互斥 Item

最开始的简化方案是：一个 Item 参与过任何效果，就不能再参与下一条效果。  
这个规则能防三持，但会误伤未来构筑深度。

比如未来一把手枪可以：

- 左边和另一把手枪触发 `DualWield`
- 右边连接芯片获得 `FireRateBoost`

这两个效果不是同一种互斥关系，应该可以共存。  
所以本课把解析器升级成“按效果类型处理”的雏形：目前只写 `DualWield` 的互斥规则，后续可堆叠效果在接入真实收益时再追加分支。

这是 Demo 期很值得保留的设计深度：不是把所有问题一次做完，而是把扩展方向设计正确。

### 5. 为什么 UI 要显示 validEffects 而不是 candidateEffects

`candidateEffects` 表示“规则上匹配到了”。  
`validEffects` 表示“本轮真的生效”。

玩家看到的金色接口应该代表系统兑现的收益，而不是候选可能性。  
否则 UI 会变成虚假承诺。

本课把 UI 改为读取 `validEffects`，让表现层和战斗层统一到同一个真实结果。

## 五、踩坑记录

### 1. 规则藏在 UI 里会导致战斗层无法复用

第14课的邻接规则最初放在 `InventoryUIController` 中，这是为了快速做出表现。  
但第21课要让战斗消费邻接效果时，规则必须从 UI 中抽离。

沉淀规则：

```text
规则是事实层，UI 是投影层。
事实不能藏在投影里。
```

### 2. 只扫描候选效果会让三把手枪 UI 误亮

三把手枪横排时，`ScanAdjacency()` 扫到两组候选很合理。  
问题不是扫描错了，而是 UI 不应该直接显示候选效果。

沉淀规则：

```text
候选效果用于推导，真实效果用于兑现和展示。
```

### 3. readonly List 不等于只读规则表

`readonly List<T>` 只能保证字段引用不被替换，不能阻止外部调用 `.Add()`、`.Clear()`。  
规则表作为事实源，应该暴露 `IReadOnlyList<T>`。

沉淀规则：

```text
只读引用 ≠ 只读集合。
```

### 4. 双持额外激活必须复用 TryActivateItem

如果双持额外激活自己写一套“找槽位、SetActive、Add HashSet”的逻辑，之后 UI 标记和场景武器很容易错位。  
本课把激活入口统一成 `TryActivateItem()`，基础激活和双持激活都走同一条路径。

沉淀规则：

```text
同一种状态变化，只保留一个入口。
```

## 六、面试问答

**Q1：你这个背包系统的构筑效果是怎么生效的？**

A：背包纯数据层先用 `InventoryGrid.ScanAdjacency()` 根据规则表扫描候选效果，再由 `AdjacencyEffectResolver` 把候选效果解析成真实有效效果。战斗层消费真实效果，例如 `DualWield` 可以突破默认自动武器上限，额外激活相邻手枪；UI 层也读取同一个有效效果列表，所以玩家看到的金色接口和战斗收益一致。

**Q2：为什么要有 AdjacencyEffectResolver，不能扫描到就直接生效吗？**

A：不能直接生效，因为候选匹配不等于真实结算。比如三把手枪横排会扫描到两组双持候选，但设计上每个手枪只能参与一组双持。Resolver 的职责就是处理互斥、优先级、堆叠限制这些“结算规则”。

**Q3：三把手枪横排时你怎么防止三持？**

A：`DualWield` 解析时使用 `HashSet<Item>` 记录已经参与过双持的物品。候选效果按背包扫描顺序进入 resolver，先被接受的一组占用两个 Item，后续如果再包含已占用 Item 就跳过。这样保留了位置优先级，也避免连锁三持。

**Q4：同一个物品未来能不能同时参与多种邻接效果？**

A：可以。当前实现只对 `DualWield` 使用 Item 互斥。未来 `FireRateBoost`、`CritBoost` 等效果会按自己的规则进入解析器，不会因为同一个 Item 参与了双持就被全局排除。这个设计把“效果类型互斥”和“物品全局互斥”区分开了。

**Q5：为什么 UI 不直接显示 ScanAdjacency 的结果？**

A：因为 `ScanAdjacency` 返回的是候选效果，而不是最终生效效果。UI 如果显示候选，就会出现看起来触发但战斗没兑现的问题。现在 UI 显示 resolver 输出的 `validEffects`，玩家看到的金色接口就是系统真实认可的效果。

**Q6：DualWield 为什么不直接把武器上限永久 +1？**

A：因为这样收益会脱离具体摆法。当前设计是基础激活先按背包位置优先级决定，然后 DualWield 只激活已激活武器的邻接伙伴。这样玩家需要通过布局触发收益，背包空间管理才有意义。

## 七、习惯清单

- 规则不要藏在 UI 里；能被多个系统消费的规则要上移到事实层。
- UI 显示“真实有效结果”，不要显示“候选中间结果”。
- 同一类状态变化只保留一个入口，例如武器激活统一走 `TryActivateItem()`。
- `readonly List<T>` 不等于只读集合，对外暴露优先用 `IReadOnlyList<T>`。
- 新增邻接效果时先问：这是互斥、可堆叠、限层数，还是只做表现？
- Demo 期可以做最小实现，但要给未来扩展留下清晰边界。
- commit 前继续扫 `UnityEditor` / `ShadowCascadeGUI` using。

## 八、思考题（附参考）

### 1. 为什么 `DualWield` 要放在 resolver 里防三持，而不是在 UI 里防？

参考答案：  
因为防三持是规则结算，不是表现问题。UI 只是展示真实结果，如果 UI 自己防，战斗层还可能生效两组；如果战斗层自己防，UI 又可能显示两组。resolver 是统一事实源，最适合承载这类结算规则。

### 2. 如果未来 `FireRateBoost` 可以叠加 3 层，你会怎么改 resolver？

参考答案：  
可以给每种 `EffectId` 单独写解析分支，或引入 `EffectRule` / `EffectStackPolicy`。`FireRateBoost` 分支用计数字典记录每个目标 Item 已经获得几层，超过 3 层就跳过。不要复用 `DualWield` 的 `usedItems`，因为两个效果的互斥规则不同。

### 3. 为什么 `DualWield` 不处理两个 Item 都未激活的情况？

参考答案：  
因为本课定义的 DualWield 是“已激活武器的邻接奖励”。如果两个都未激活也能触发，就会绕过背包位置优先级，让右下角武器免费激活。这样背包排序和构筑规则会互相打架。

### 4. 如果场景里只配了一个 Pistol WeaponSlot，两把相邻手枪会怎样？

参考答案：  
代码不会报错，但只能激活一个场景武器对象。`TryActivateItem()` 会跳过已经 active 的 WeaponObject，找不到第二个可用 Pistol 槽位就返回 false。这属于场景接线资源不足，不是背包规则错误。
