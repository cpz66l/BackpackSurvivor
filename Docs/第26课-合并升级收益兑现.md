# 第26课 · 合并升级收益兑现

> 课程周期：2026-08-03  
> 前置：第25课《背包价值与物品价值显示》  
> 关键词：合并收益、基础值与当前值、EffectValue、FireRateBoost、Tooltip、数值平衡

---

## 一、这节课实现了什么

第26课把“合并升级”从视觉等级，推进成了真正影响收益的系统。  
现在 Lv.2 / Lv.3 物品不只是显示等级更高，它们的背包价值和战斗效果也会随等级成长。

### 任务 1 · Item 拆出基础值与当前值

- `Item` 新增 `baseScoreValue` 和 `baseEffectValue`。
- `ScoreValue` 改成 `baseScoreValue * Level`。
- `EffectValue` 改成 `baseEffectValue * Level`。
- 对外暴露 `BaseScoreValue / BaseEffectValue`，给丢弃还原使用。

这一步的核心是把“配置初始值”和“运行时当前值”分开。  
配置表给 Lv.1 的基础值，运行时等级决定当前收益。

### 任务 2 · 合并升级自动兑现价值和效果

- `InventoryGrid.TryMerge(source, target)` 仍然只调用 `target.IncreaseLevel()`。
- 因为 `ScoreValue / EffectValue` 是计算属性，所以等级变化后收益自然变化。
- 背包总价值、结算页、Tooltip、邻接效果消费侧都不需要额外同步。

这是本课最舒服的一点：把规则放在 `Item` 里，消费侧继续读同一个属性，系统会自动更新。

### 任务 3 · 丢弃路径改为还原基础值

- `DiscardToWorld()` 还原 `LootEntry` 时写 `item.BaseScoreValue`。
- `effectValue` 同样写 `item.BaseEffectValue`。
- 避免 Lv.2 物品丢出去再捡回来，变成“Lv.1 但基础值翻倍”的污染物品。

当前 Demo 取舍是：Lv.2 丢出再捡回会回到 Lv.1。  
这不是最终形态，但比“运行时等级污染静态配置”更安全。

### 任务 4 · FireRateBoost 读取升级后的 EffectValue

- `BackpackWeaponActivator.ActivateFireRateBoost()` 继续读取邻接物品的 `item.EffectValue`。
- 因为 `EffectValue` 已随等级成长，Lv.2 弹夹能提供更高攻速加成。
- `maxBackpackFireRateMultiplier` 从硬编码改为序列化字段，便于 Demo 调参。

这让“弹夹合并升级”能被战斗系统真实感知。

### 任务 5 · 物品详情从格子内迁移到 Tooltip

- 新增 `ItemTooltipView`。
- `ItemView` 增加 `IPointerEnterHandler / IPointerMoveHandler / IPointerExitHandler`。
- `InventoryUIController` 提供 `ShowTooltip / MoveTooltip / HideTooltip` 桥接。
- 格子内只保留物品名和等级，详细信息放到悬停面板。

这一步是 UI 信息分层：格子负责扫一眼，Tooltip 负责读细节。

### 任务 6 · 修复伤害数字向上取整误导

- 发现伤害数字显示 25，但 50 血敌人需要 3 枪。
- 根因是显示层用了 `Mathf.CeilToInt(damage)`，真实扣血仍是浮点伤害。
- 当前改为不向上夸大显示，避免 UI 给玩家错误预期。

正式方案应在后续数值课统一决定：伤害源头整数化，还是 UI 显示一位小数。

## 二、最终代码（关键片段）

### 1. Item 保存基础值，当前值随等级计算

```csharp
private readonly int baseScoreValue;
private readonly float baseEffectValue;

public int ScoreValue => baseScoreValue * Level;
public float EffectValue => baseEffectValue * Level;
public int BaseScoreValue => baseScoreValue;
public float BaseEffectValue => baseEffectValue;
```

这里的设计重点是：  
`baseScoreValue / baseEffectValue` 是 Lv.1 配置值，`ScoreValue / EffectValue` 是运行时当前值。

### 2. 构造 Item 时保存基础值

```csharp
public Item(
    string id,
    Rarity rarity,
    int width,
    int height,
    ItemTag itemTag,
    ConnectableSides connectableSides,
    int scoreValue,
    float effectValue)
{
    Id = id;
    baseWidth = width;
    baseHeight = height;
    Rarity = rarity;
    Rotated = false;
    Level = 1;
    MaxLevel = 3;
    Tag = itemTag;
    LocalConnectableSides = connectableSides;
    baseScoreValue = scoreValue;
    baseEffectValue = effectValue;
}
```

参数仍然叫 `scoreValue / effectValue`，因为从 `LootEntry` 传进来时它们代表 Lv.1 的配置基础值。  
进入 `Item` 后，就变成 `baseScoreValue / baseEffectValue`。

### 3. 合并只提升等级，收益自然变化

```csharp
public bool TryMerge(Item source, Item target)
{
    if (!CanMerge(source, target)) return false;
    target.IncreaseLevel();
    Remove(source);
    return true;
}
```

`TryMerge()` 不需要手动改价值，也不需要手动改效果值。  
因为 `ScoreValue / EffectValue` 读的是 `Level`，`Level++` 后所有消费方都会读到新结果。

### 4. 丢弃时还原基础值

```csharp
LootEntry entry = new LootEntry
{
    category = DropCategory.Equipment,
    id = item.Id,
    rarity = item.Rarity,
    width = item.Width,
    height = item.Height,
    amount = 1,
    itemTag = item.Tag,
    connectableSides = item.LocalConnectableSides,
    scoreValue = item.BaseScoreValue,
    effectValue = item.BaseEffectValue,
};
```

这里故意不用 `item.ScoreValue / item.EffectValue`。  
否则 Lv.2 丢出再捡回，会创建一个 Lv.1 但基础值已经翻倍的新物品，后续再升级会越滚越离谱。

### 5. FireRateBoost 消费当前效果值

```csharp
if (TryGetActiveAutoWeapon(effect.ItemA, out AutoWeapon autoWeaponA))
{
    float effectValue = effect.ItemB.EffectValue;
    if (fireRateBonusByWeapon.ContainsKey(autoWeaponA))
        fireRateBonusByWeapon[autoWeaponA] += effectValue;
    else
        fireRateBonusByWeapon[autoWeaponA] = effectValue;
}
```

攻速芯片读的是 `EffectValue`，所以合并升级会自动影响战斗收益。  
这也是“运行时当前值”设计的价值。

### 6. 攻速上限改成可调字段

```csharp
[SerializeField] private float maxBackpackFireRateMultiplier = 2.5f;

float fireRateMultiplier = 1f + effectValues;
fireRateMultiplier = Mathf.Min(fireRateMultiplier, maxBackpackFireRateMultiplier);
autoWeapon.SetBackpackFireRateMultiplier(fireRateMultiplier);
```

第26课后弹夹升级收益已经生效，所以硬编码上限会直接影响手感。  
把上限暴露出来，是为了第27课做首轮平衡。

### 7. ItemTooltipView 展示当前物品信息

```csharp
titleText.text = $"{item.Id} (Lv.{item.Level})";

if (item.EffectValue > 0)
{
    int percent = Mathf.RoundToInt(item.EffectValue * 100f);
    bodyText.text = $"稀有度: {item.Rarity}\n" +
                    $"大小: {item.Width}x{item.Height}\n" +
                    $"价值: ￥{item.ScoreValue}\n" +
                    $"效果: +{percent}%";
}
else
{
    bodyText.text = $"稀有度: {item.Rarity}\n" +
                    $"大小: {item.Width}x{item.Height}\n" +
                    $"价值: ￥{item.ScoreValue}";
}
```

Tooltip 显示的是当前值。  
Lv.2 物品悬停时，价值和效果都应该是升级后的结果。

### 8. ItemView 只保留轻量信息

```csharp
label.text = $"{item.Id} \r\n" +
    $" Lv.{item.Level}";
```

格子空间很小，继续塞价值、效果、稀有度会影响背包可读性。  
所以 ItemView 只保留最关键识别信息，详细内容交给 Tooltip。

### 9. 鼠标悬停驱动 Tooltip

```csharp
public void OnPointerEnter(PointerEventData eventData)
{
    controller.ShowTooltip(item, eventData.position);
}

public void OnPointerMove(PointerEventData eventData)
{
    controller.MoveTooltip(eventData.position);
}

public void OnPointerExit(PointerEventData eventData)
{
    controller.HideTooltip();
}
```

这保持了 `ItemView` 的“木偶”身份。  
它只把鼠标事件传给控制器，不自己决定面板生命周期之外的复杂逻辑。

### 10. 拖拽期间不显示 Tooltip

```csharp
public void ShowTooltip(Item item, Vector2 screenPosition)
{
    if (isDragging) return;
    tooltipView?.Show(item, screenPosition);
}
```

拖拽时鼠标下面已经有 ghost，再显示 Tooltip 会干扰玩家判断。  
所以悬停信息只服务“查看”，不服务“拖动”。

### 11. 伤害数字不再向上夸大

```csharp
public void Play(float damage)
{
    if (damageText != null)
        damageText.text = Mathf.FloorToInt(damage).ToString();

    if (playRoutine != null)
        StopCoroutine(playRoutine);

    playRoutine = StartCoroutine(PlayRoutine());
}
```

这不是最终数值格式方案，只是先避免“显示 25，实际不到 25”的误导。  
后续第27课会统一处理伤害取整与怪物血量成长。

## 四、设计思考

### 1. 为什么要区分 BaseValue 和 CurrentValue？

如果只有一个 `ScoreValue` 字段，升级时有两种坏味道：

```text
方案 A：升级时直接改字段
问题：谁负责改？漏改一个消费侧就不同步。

方案 B：丢弃时把当前值写回 LootEntry
问题：运行时状态污染静态配置，捡回来会变成伪 Lv.1 高基础值物品。
```

所以更干净的结构是：

```text
BaseValue = 配置给的 Lv.1 数值
Level = 运行时等级
CurrentValue = BaseValue * Level
```

这样运行时值始终由基础值和等级推导出来。

### 2. 为什么 TryMerge 不直接写 ScoreValue？

`TryMerge()` 的职责是“两个物品是否能合并，以及合并后哪个物品留下”。  
它不应该顺手管理所有升级收益。

如果未来合并收益从线性改成曲线，例如：

```text
Lv.1 = 100%
Lv.2 = 160%
Lv.3 = 240%
```

我们应该改 `Item` 的收益公式或引入成长表，而不是在 `TryMerge()` 到处写加法。

### 3. 为什么当前丢弃 Lv.2 会回到 Lv.1？

因为现在 `LootEntry` 仍然是静态掉落数据结构，没有承载运行时等级。  
强行把 Lv.2 当前值写进 `LootEntry`，会让再次拾取的物品变成“Lv.1 外壳 + Lv.2 数值”。

Demo 阶段我们选择更安全的取舍：

```text
丢弃升级物品会损失等级
但不会污染物品基础数据
```

正式版本可以新增 `DropRuntimeData` 或让地面掉落承载 `level`，再解决完整往返保真。

### 4. 为什么 Tooltip 比格子内显示更适合？

背包格子的第一职责是让玩家快速判断：

```text
这是什么物品？
几级？
占几格？
能不能拖？
有没有接口/激活状态？
```

价值、效果、稀有度、尺寸属于“查看详情”。  
如果全部塞在格子里，信息反而更难读。

所以 UI 分层是：

```text
ItemView = 快速识别
Tooltip = 详细理解
ResultView / TotalValueText = 总结反馈
```

### 5. 为什么第27课必须做数值平衡？

第26课后，弹夹的 `EffectValue` 会乘等级。  
如果基础弹夹已经给 40%~45% 攻速，Lv.2 直接变成 80%~90%，再叠加攻速上限，就很容易超模。

同时怪物血量目前没有随波次稳定成长，玩家成长起来后会越来越碾压。  
所以第27课不能只是“调几个数字”，而要建立首轮平衡框架：

```text
玩家成长：升级 / 合并 / 邻接
敌人成长：血量 / 数量 / 精英率 / 宝箱期望
体验目标：前期爽，中期有压力，后期不白给
```

## 五、踩坑记录

### 1. 升级收益不能只改 UI

- **现象风险**：物品显示 Lv.2，但价值和效果仍然是 Lv.1。
- **根因**：等级只是状态，如果消费侧不读等级参与计算，升级没有真实意义。
- **修复**：`ScoreValue / EffectValue` 改为由基础值乘等级得到。
- **沉淀**：能影响玩家决策的等级，必须影响至少一个真实收益。

### 2. 当前值不能写回静态掉落字段

- **现象风险**：Lv.2 物品丢出再捡回，变成 Lv.1 但基础数值翻倍。
- **根因**：把运行时当前值当成静态配置值写回 `LootEntry`。
- **修复**：丢弃时写 `BaseScoreValue / BaseEffectValue`。
- **沉淀**：运行时状态不要污染配置数据；要完整保真就单独设计 RuntimeData。

### 3. 硬编码攻速上限会压扁升级体感

- **现象风险**：Lv.1、Lv.2 弹夹理论效果不同，但都被同一个上限截断，玩家感觉不明显。
- **根因**：`1.75f` 写死在代码里，且升级后收益很容易撞上天花板。
- **修复**：改成 `maxBackpackFireRateMultiplier` 序列化字段。
- **沉淀**：Demo 冲刺期的核心数值上限要可调，不要藏在代码里。

### 4. 格子里塞太多信息会降低可读性

- **现象风险**：小格子里同时显示名称、等级、价值、效果，文字挤压背包识别。
- **根因**：没有区分“扫视信息”和“详情信息”。
- **修复**：格子只保留名称/等级，详细属性放到悬停 Tooltip。
- **沉淀**：UI 信息要分层，背包格子不是说明书。

### 5. 显示伤害不能向上承诺

- **现象**：显示 25 伤害，但 50 血敌人要 3 枪。
- **根因**：显示层 `CeilToInt`，真实扣血仍是 24.x 浮点。
- **修复**：临时改为不向上夸大；正式方案留给数值课统一处理。
- **沉淀**：战斗 UI 不要 overpromise；显示值和真实规则必须语义一致。

## 六、面试问答

**Q1：你怎么让合并升级影响价值和效果？**  
> 我把物品的基础值和当前值拆开。`baseScoreValue / baseEffectValue` 保存 Lv.1 配置值，`ScoreValue / EffectValue` 作为计算属性返回基础值乘当前 `Level`。这样合并时只需要提升等级，UI、结算和战斗消费侧都会自然读到升级后的收益。

**Q2：为什么不在 TryMerge 里直接修改 ScoreValue？**  
> 因为 `TryMerge` 的职责是合并规则，不应该知道所有收益公式。把收益公式集中在 `Item` 里，后续无论是线性成长还是曲线成长，都只需要改一个事实源，消费侧不用变。

**Q3：为什么丢弃物品时写 BaseScoreValue，而不是 ScoreValue？**  
> `ScoreValue` 是当前运行时值，包含等级加成；`LootEntry.scoreValue` 是静态基础值。如果把当前值写回去，Lv.2 物品再捡回来会变成 Lv.1 但基础值翻倍。当前 Demo 选择丢弃后等级丢失，但保证基础配置不被污染。

**Q4：FireRateBoost 为什么能自动吃到升级收益？**  
> 攻速加成消费侧一直读邻接物品的 `EffectValue`。当 `EffectValue` 改成随等级计算后，Lv.2 弹夹自然返回更高效果，不需要在 `BackpackWeaponActivator` 里额外判断等级。

**Q5：为什么要把攻速上限做成 SerializeField？**  
> 因为第26课后升级收益可能让攻速很快撞上上限。上限如果硬编码，调参要反复改代码；做成序列化字段后，可以在 Unity 里快速找到合适手感。

**Q6：为什么要做 Tooltip，而不是继续在格子里显示效果？**  
> 背包格子面积小，应该服务快速识别。价值、效果、稀有度、尺寸属于详情信息，放在悬停 Tooltip 更清楚，也不会影响拖拽和邻接接口的可读性。

**Q7：伤害数字显示 bug 说明了什么？**  
> 显示层不能和规则层产生语义偏差。真实伤害是 24.x 时，向上显示 25 会让玩家以为两枪能打死 50 血敌人。战斗反馈必须尽量忠实，否则玩家会觉得系统“不讲理”。

## 七、习惯清单

1. 配置基础值和运行时当前值要拆开。
2. 合并升级优先改等级，收益由统一公式推导。
3. 新增等级收益后，所有消费侧尽量继续读同一个属性。
4. 丢弃、拾取、结算这些边界路径要重新查字段语义。
5. 运行时当前值不要写回静态配置字段。
6. Demo 期关键数值上限尽量暴露成可调参数。
7. UI 信息分层：格子扫视，Tooltip 详情，结算总结。
8. 纯展示 Tooltip 要关闭射线阻挡，拖拽时主动隐藏。
9. 战斗显示值不能向上夸大真实规则。

## 八、思考题（附复习参考）

**Q1：如果 Lv.2 不是 2 倍，而是 1.6 倍，应该怎么改？**  
> 不要改 `TryMerge()`。应该在 `Item` 里抽出成长倍率公式，例如 `GetLevelMultiplier()`，或后续接入成长表。消费侧仍然读 `ScoreValue / EffectValue`。

**Q2：为什么当前丢弃 Lv.2 物品会回到 Lv.1，而不是保留等级？**  
> 因为 `LootEntry` 目前是静态配置结构，没有保存运行时 `Level`。为了避免当前值污染基础值，先选择丢弃损失等级。正式版本可以设计 `DropRuntimeData` 保存 `level/baseValue/rotation` 等运行时状态。

**Q3：弹夹升级后为什么容易超模？**  
> 因为攻速是乘法型体验收益。基础弹夹如果已经给 40%，Lv.2 就可能到 80%，再叠加玩家升级、武器本身射速和多芯片联动，DPS 会非线性膨胀。下一课需要降低基础值、调整等级曲线或提高敌人成长。

**Q4：为什么怪物血量也应该随波次成长？**  
> 玩家已经有经验升级、背包合并、邻接芯片三条成长线。如果敌人只增加数量，不增加质量，后期会变成割草无压力。血量随波次成长可以延长 TTK，让后期仍有压力。

**Q5：Tooltip 里显示“效果 +80%”有什么设计风险？**  
> 玩家会把它理解成非常强的承诺。如果实际因为上限、互斥或未激活导致没有完整生效，就会产生认知落差。后续最好区分“物品属性”和“当前生效收益”。
