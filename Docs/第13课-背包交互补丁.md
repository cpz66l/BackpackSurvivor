## 一、这节课实现了什么

### 任务 1 · 提示框吃射线（BUG-006）

- 根因：`PromptPanel` 锚点全屏拉伸 + 透明 Image + RaycastTarget 默认开 → 提示框一显示，全屏射线被吞，背包拖不动
- 修法：纯展示元素射线一刀切——CanvasGroup `blocksRaycasts = false` 系统化管理，替代逐个揪 RaycastTarget
- 规则升级：**不响应点击的 UI 元素射线一律不通；用 CanvasGroup 批量管，不靠逐个记忆**

### 任务 2 · 丢弃功能（散落协程第二次就业）

- `LootManager` 提炼公共生成口 `SpawnEntry(entry, pos)`（开闭原则第三次实践：先提炼、验旧、再接新）
- 拖拽第三结局：面板外松手 = 世界丢弃（`RectangleContainsScreenPoint` 判定，插在 CanPlaceAt 链最前）
- `InventorySystem.DiscardToWorld`：Item→LootEntry 还原（往返保真）→ SpawnEntry → PlayScatterFlight 抛物线
- ghost 手动销毁（丢弃分支无 Place → 无 OnChanged → 没人替你 Redraw）

### 任务 3 · R 键旋转

- `Item` 加 `Rotated` 标志位：baseWidth/baseHeight 存原值，`Width/Height` 属性按标志换算——**只读契约保住，下游零改动**（封装红利第二次兑现）
- 输入：`Rotate` action 绑 R → `InputReader.OnRotate` 事件
- `InventoryUIController.HandleRotate`：只转手上拖着的（塔科夫规矩），ghost 尺寸+红绿判定即时重算
- 踩坑：OnEnable 早于 Start 导致订阅时引用未就位 → NRE 订阅失败（BUG-008）

### 任务 4 · 收货口请求-确认（吞物品治本）

- **接口演进**：`IInteractable.Interact()` 从 `void` 改 `bool`——破坏性变更，编译器报错清单当施工清单（两个实现类+探测器三处）
- `InventorySystem.CanAccept`：侦察兵只问不放，构造探针试 `TryFindFreeArea`
- `DropItem.Interact()`：先问后收——能则 `Collect()` 返 true；不能留地上返 false
- `InteractDetector`：成功才清目标（BUG-005 的"用完即清"有了正确时机）；失败广播 `OnInteractFailed` → 闪字"背包已满"（协程第三次就业）
- **双保险**：`HandleCollected` 满包兜底 `DiscardToWorld` 吐回地上（用户自主发挥，好评）
- `TryFindFreeArea` 内置双朝向查找：原朝向找不到→旋转再找→双失败转回原样（**副作用只在成功时留下，失败物归原样**——用户方案+契约诚实化）

### 任务 5 · 轻量优化

- `MapBounds` 迁 `Scripts/Core/` → `BS.Core`（消费方早有 using，零改动通过）
- `Faction.neutral` → `Faction.Neutral`（编译器带你找引用）
- using 强制闸执行

## 二、最终代码（关键片段）

### Item.cs（Rotated 标志位，纯 C# 程序集零 UnityEngine）

```csharp
public class Item
{
    public string Id { get; }
    public Rarity Rarity { get; }
    public bool Rotated { get; private set; }

    private readonly int baseWidth;    // 原始朝向存一份不动
    private readonly int baseHeight;

    public int Width => Rotated ? baseHeight : baseWidth;   // 数据一份，表现按需换算
    public int Height => Rotated ? baseWidth : baseHeight;

    public Item(string id, Rarity rarity, int width, int height)
    {
        Id = id; Rarity = rarity;
        baseWidth = width; baseHeight = height;
        Rotated = false;
    }

    public void Rotate() => Rotated = !Rotated;
}
```

### InventoryGrid.TryFindFreeArea（双朝向 + 诚实契约）

```csharp
// 契约：找到位置时，item 可能已被旋转到匹配朝向（供后续 Place 使用）；
//       没找到时，item 保持原样，什么都不动。
public bool TryFindFreeArea(Item item, out int x, out int y)
{
    /* 第一趟：原朝向扫描，找到 → 赋值返回 true */
    item.Rotate();          // 第二趟：反转再找
    /* 找到 → 赋值返回 true */
    item.Rotate();          // 双失败：转回去，物归原样
    x = y = -1;
    return false;
}
```

### InventorySystem.cs（侦察兵 + 丢弃 + 兜底吐回）

```csharp
// 许可侦察兵：只问不放（注：TryFindFreeArea 内置双朝向后，外层 Rotate 已冗余，可删）
public bool CanAccept(LootEntry entry)
{
    if (entry == null) return false;
    Item probe = new Item(entry.id, entry.rarity, entry.width, entry.height);
    if (Grid.TryFindFreeArea(probe, out _, out _)) return true;
    probe.Rotate();
    return Grid.TryFindFreeArea(probe, out _, out _);
}

private void HandleCollected(LootEntry entry)
{
    if (entry == null) return;
    Item item = new Item(entry.id, entry.rarity, entry.width, entry.height);
    if (Grid.TryFindFreeArea(item, out int x, out int y)) Grid.Place(x, y, item);
    else DiscardToWorld(item);            // 双保险：兜底吐回地上，永不吞物品
}

public void DiscardToWorld(Item item)
{
    LootEntry entry = new LootEntry       // Item → LootEntry 还原，往返保真
    {
        category = DropCategory.Equipment,
        id = item.Id, rarity = item.Rarity,
        width = item.Width, height = item.Height, amount = 1
    };
    Vector3 from = playerHealth.Position;
    GameObject go = lootManager.SpawnEntry(entry, from);
    Vector2 offset = Random.insideUnitCircle * 2f;
    Vector3 to = new Vector3(from.x + offset.x, 0.5f, from.z + offset.y);
    go.GetComponent<DropItem>()?.PlayScatterFlight(from, to);
}
```

### InventoryUIController.EndDrag（三结局，面板判定最优先）

```csharp
public void EndDrag(Vector2 pointerPos)
{
    if (!isDragging) return;
    isDragging = false;

    // 面板外松手 = 丢弃（第三结局，插在 CanPlaceAt 链最前）
    if (!RectTransformUtility.RectangleContainsScreenPoint(bagPanel, pointerPos, null))
    {
        inventorySystem.DiscardToWorld(dragItem);
        Destroy(ghost.gameObject);   // 无 Place → 无 OnChanged → 没人替你 Redraw
        dragItem = null;
        ghost = null;
        return;
    }

    if (grid.CanPlaceAt(targetX, targetY, dragItem)) grid.Place(targetX, targetY, dragItem);
    else if (grid.CanPlaceAt(oldX, oldY, dragItem)) grid.Place(oldX, oldY, dragItem);   // 回滚
    else if (grid.TryFindFreeArea(dragItem, out int fx, out int fy) && grid.Place(fx, fy, dragItem)) { }   // 旧位被占找新空位
    else   // 包满：兜底丢弃到世界（同面板外分支：无 Place 无 OnChanged，ghost 手动销毁）
    {
        inventorySystem.DiscardToWorld(dragItem);
        Destroy(ghost.gameObject);
        dragItem = null;
        ghost = null;
        return;
    }
    dragItem = null;
    ghost = null;
}
```

// InteractDetector：成功才清目标，失败广播闪字
private void Interact()
{
    if (CurrentTarget == null) return;
    if (!CurrentTarget.Interact()) { OnInteractFailed?.Invoke(); return; }
    previousTarget = null; CurrentTarget = null;
    OnTargetChanged?.Invoke(null);
}

## 三、周期链路

### 丢弃闭环（背包 ⇄ 世界 双向打通）

```
拖起物品（BeginDrag：Remove 离包）
  → 拖到面板外松手 → EndDrag 第一分支
  → DiscardToWorld：Item→LootEntry 还原 → SpawnEntry → 玩家胸口生成
  → PlayScatterFlight → 抛物线落身旁 → 落地开碰撞器
  → ghost 手动销毁，背包格子真正空出
  → （任意时刻）走近 → E → CanAccept → Collect → 入包（往返保真）
```

### 请求-确认拾取链路

```
按 E → detector.Interact() → CurrentTarget.Interact()
  → DropItem 问 InventorySystem.CanAccept（探针双朝向试放）
    → 能：Collect()（广播+回池）→ 返 true → 探测器清目标、提示隐藏
    → 不能：返 false → 目标保留、提示保留 → OnInteractFailed → 闪字 0.5s
  → （双保险）HandleCollected 真遇到满包 → DiscardToWorld 吐回地上
```

### 旋转链路（一改全通）

```
拖拽中按 R → InputReader.OnRotate → HandleRotate
  → dragItem.Rotate()（标志翻转）
  → Width/Height 换算属性自动交换
  → ghost 尺寸重设 + CanPlaceAt 红绿重算
  → 放下：Place/CanPlaceAt 读换算后宽高 → 占格正确
  → 再拿起：Rotated 随实例持久 → 仍是旋转态
```

## 四、设计思考（这节课真正学的东西）

### 1. 封装的红利第二次兑现

`Item` 宽高只读 + `Rotated` 标志位换算，下游网格判定、UI 尺寸、红绿预览**一行没改**全跟着对了。对比方案复盘：破只读让外部乱改（契约崩坏）❌；new 实例换引用（网格/UI 持有旧引用换不动）❌。结论：**数据存一份，表现按需换算；状态用标志位表达，不用值覆盖表达**。

### 2. 开闭原则已经长成肌肉记忆

`SpawnEntry` 提炼是第三次"先提炼、验旧、接新"（前两次：TrySpawnDrop 改返回值、束结构）。每次新需求来，第一刀都落在"给老代码开一扇门"而不是"给老代码动一次手术"。丢弃、宝箱、以后商店/GM 工具，全走同一个生成口。

### 3. 接口演进的学费与施工法

`Interact(): void → bool` 是破坏性变更：先改接口，**让编译器报错清单当施工清单**（本课=三处），清零才收工。教训反哺设计：接口签名想远一步——"交互"天然可能有结果，初版 `void` 是想浅了。但想太远也错（YAGNI），平衡点是：**为可预见的一阶变化留空间，不为幻想中的二阶变化付现价**。

### 4. 副作用契约诚实（用户方案的案例教学）

用户的 `TryFindFreeArea` 双朝向方案方向正确（朝向必须跟着查找结果走），但裸版有两个雷：查询方法藏副作用、双失败残留旋转。诚实化补丁：**副作用只在成功且有意义时留下，失败路径物归原样**。方法退出时，世界要么按承诺改变，要么分毫未动，没有中间态。

### 5. 镜像原则（这节课最大的习惯收获）

三处事故同一病根：**只做了"开"，没做对"关"**——订阅 += 有了退订写成 +=（不镜像）；闪字点亮了关的却是面板（不镜像）；OnEnable 订阅时引用还没就位（顺序不镜像）。以后写任何成对操作——订阅/退订、点亮/熄灭、加锁/解锁、注册/注销——**写完立刻镜像审查：两行逐字符对比**。

### 6. 吞物品漏洞的治本 + 双保险

治本=请求-确认（前端不让收）；双保险=兜底吐回（后端真收了也吐出来）。用户的自主发挥恰好是防御纵深的教科书：**关键资源（玩家的物品），永远不要只有一个保护点**。

## 六、面试问答

**Q：Awake / OnEnable / Start 的执行顺序和使用分工？**
A：顺序 Awake → OnEnable → Start。分工：Awake 拿自己的组件引用、new 内部数据（不依赖别人就绪）；OnEnable 订阅事件/注册（引用必须已就位，所以引用缓存放 Awake）；Start 拿**别的对象**的引用、依赖他人初始化的逻辑（此时别人的 Awake 已跑完）。实际踩坑：订阅放 OnEnable、引用赋值放 Start → 订阅时 NRE，功能静默失效，报错埋在游戏启动的第一帧。

**Q：物品旋转怎么建模的？为什么不直接交换宽高？**
A：加 `Rotated` 布尔标志，宽高变成按标志换算的计算属性，原始尺寸存一份不动。直接交换宽高要破只读契约（外部可乱改）；new 新实例则网格和 UI 都持有旧引用换不动。标志位方案：数据存一份、表现按需换算，下游零改动。这是"单一事实源"思想在数据建模上的应用。

**Q：`IInteractable.Interact()` 从 void 改成 bool，以后有"长按 3 秒读条开箱"怎么办？**
A：bool 只够表达"瞬时成败"。读条交互是**过程**不是结果——接口需要演进成交互会话：比如 `Interact()` 返回交互句柄/token，或拆成 `BeginInteract/CancelInteract/交互进度事件`。这就是接口设计的难点：改签名是破坏性变更，所有实现类跟着疼。经验法则是为一阶可预见变化留空间（当时就看出"交互可能有结果"该留返回值），不为幻想中的二阶变化提前付现。

**Q：拖拽丢弃怎么判定"拖出面板"？可拖动窗口下还成立吗？**
A：`RectTransformUtility.RectangleContainsScreenPoint(panelRect, pointerPos, null)` 做矩形包含测试。可拖动窗口下依然成立——RectTransform 跟着窗口动，测试用的是实时矩形。这正是选 UI 坐标系 API 而非手写屏幕坐标判断的原因：**跟着 RectTransform 走的判定，天然免疫布局变化**。

**Q：隐形 UI 挡点击怎么系统性防御？**
A：个案是"透明 Image 开 RaycastTarget 吞射线"。系统解法：不响应点击的元素统一挂 CanvasGroup `blocksRaycasts=false` 批量管理，而不是逐个揪 RaycastTarget 靠记忆。推广规则：**交互豁免要显式声明，不靠默认值的偶然正确**。

**Q："承诺与兑现一致性"是什么？举个你项目里的例子。**
A：系统对外承诺的能力，必须在兑现路径上完全兑现。案例：预审 `CanAccept` 试放时允许旋转朝向，但入包 `TryFindFreeArea` 原本只按默认朝向找——预审说"能收"，兑现却"放不下"，承诺破产。修法：把双朝向查找下沉进 `TryFindFreeArea`，朝向跟着查找结果一起走，预审和兑现走同一条代码路径——**一致性最好的保障是让两者无法分叉**。

## 八、思考题（附复习参考）

**Q1：`Rotated` 标志位方案，对比"真交换宽高"和"new 新实例"各赢什么、输什么？**
> 赢：只读契约不破、下游零改动、状态随实例持久、可逆（转来转去）。输：① 语义绕一层——"宽高"不再是存储值，读代码要理解换算；② 跨边界丢失——LootEntry 不带 Rotated，丢弃再捡回恢复默认朝向（已记录的 MVP 限制）；③ 若以后有"镜像翻转"等更多形态，单 bool 不够要升级枚举。三方案没有银弹，标志位在"引用共享多、形态只有两种"时最优。

**Q2：预审试旋转通过了，入包时兑现了吗？怎么修的？**
> 最初没兑现（预审双朝向、入包单朝向，承诺破产）。解法：双朝向查找下沉进 `TryFindFreeArea`——原朝向找不到则旋转再找，双失败转回原样。关键不是"能跑"，是契约诚实：副作用只在成功时留下，失败物归原样。一致性最好的保障是让承诺与兑现走同一条代码路径，无法分叉。

**Q3：`RectangleContainsScreenPoint` 判定"面板外"，背包做成可拖动窗口还成立吗？**
> 成立。判定用的是 RectTransform 的实时矩形，窗口拖动 RectTransform 跟着动。选 UI 坐标系 API 而非手写屏幕坐标判断，就是为了免疫布局变化——这是"基于数据结构（RectTransform）而非基于快照（某时刻的屏幕坐标）做判定"的思想。

**Q4：闪字三连环里，"残留 active 子物体借爹复活"给我们什么显隐设计教训？**
> 每个对象的显隐状态要自洽：父物体隐藏只是"看不见"，不等于子物体"已关闭"。开父时残留的 active 子物体会复活。两条防线：① 熄灭路径和点亮路径镜像（点亮谁熄灭谁）；② 父物体重新显示前，不确定的子状态先复位（如 HandleTargetChanged 显示面板时先确保闪字关）。
