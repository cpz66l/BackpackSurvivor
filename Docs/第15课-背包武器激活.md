## 一、这节课实现了什么

### 任务 1 · 提交前 Demo 收口闸

- 继续执行运行时代码卫生门闸：扫描 `UnityEditor.*`、`ShadowCascadeGUI`、`Mono.Cecil`、多余 Rendering using、临时测试注释。
- 清理第 14 课遗留的调试/临时标记，让课程切换前不把“能跑但不干净”的状态滚进下一课。
- 场景规则和课程目标对齐：默认自动武器激活上限为 `1`，后续 DualWield 再负责突破上限。

### 任务 2 · 背包武器激活系统

- 新增 `BackpackWeaponActivator`，监听背包 `InventoryGrid.OnChanged`。
- 背包中出现指定武器标签时，激活玩家身边对应的自动武器对象。
- 背包中移除武器、丢弃武器、合并/重排导致优先级变化时，先关闭全部武器，再按当前背包状态重新结算。
- 用 `WeaponSlot` 把 `ItemTag` 和场景里的武器 GameObject 绑定起来，避免在逻辑里写一堆 `if-else`。

### 任务 3 · 背包位置决定激活优先级

- `InventoryGrid.GetUniqueItems()` 返回背包内唯一物品列表。
- 遍历顺序固定为从上到下、从左到右，因此越靠左上越优先激活。
- 这条规则让玩家能通过摆放位置控制当前激活武器，形成“背包整理 = 战斗选择”的可玩性。
- 本课没有引入 `Priority` 字段，也没有做手动选择 UI，因为 Demo 阶段更需要低成本、可感知、可操作的规则。

### 任务 4 · 背包内激活标记

- `BackpackWeaponActivator` 用 `HashSet<Item>` 记录当前真正激活的物品实例。
- `InventoryUIController.Redraw()` 生成 `ItemView` 时，查询该物品是否激活，并调用 `SetActiveWeapon()`。
- 选择记录 `Item` 实例，而不是只记录 `ItemTag`，是为了区分“同为手枪，但只有左上那把被激活”的情况。
- 背包 UI 现在能告诉玩家：哪个物品正在驱动玩家身边的自动武器。

### 任务 5 · 拖拽期间重绘补偿

- 拖拽开始时，物品会从数据层 `Remove`，但 UI 不能立刻全量重绘，否则手里的 ghost 会被销毁。
- `Redraw()` 在 `isDragging` 时不画，而是设置 `needsRedrawAfterDrag = true`。
- 如果拖拽最终走“面板外丢弃 / 合并 / 背包满丢弃”等不会自然触发 Place 的分支，就在清理拖拽状态后补一次 `Redraw()`。
- 修复了“丢掉被标记武器后，新顶上的武器实体已激活，但 UI 标记要等下一次重绘才出现”的感官 bug。

### 任务 6 · 接口点与激活角标自适应

- `ItemView.UpdateOverlayLayout(step)` 根据格子尺寸计算接口点、激活角标大小和内边距。
- `Bind()` 和拖拽旋转 `HandleRotate()` 后都会调用布局刷新，保证横竖物品、旋转 ghost 都能重新贴边。
- 邻接接口点继续表达“这边能不能连接 / 有没有连接成功”，激活角标表达“这个物品是否正在驱动自动武器”。
- 真实冷却遮罩暂时后移，不进入 8 月 15 Demo 冲刺主线。

## 二、最终代码（关键片段）

### 武器槽：用配置表代替 if-else

```csharp
[System.Serializable]
private class WeaponSlot
{
    public ItemTag Tag;
    public GameObject WeaponObject;
}

[SerializeField] private int activeWeaponLimit = 1;
[SerializeField] private List<WeaponSlot> weaponSlots;
```

`WeaponSlot` 的意义不是节省几行代码，而是把“什么物品对应什么武器实体”变成可配置关系。后面加步枪、霰弹枪、狙击枪时，优先改 Inspector 配置，不优先改逻辑分支。

### 刷新激活武器：先清空，再重算

```csharp
private void RefreshActiveWeapons()
{
    foreach (var weapon in weaponSlots)
    {
        if (weapon == null) continue;
        if (weapon.WeaponObject == null) continue;
        weapon.WeaponObject.SetActive(false);
    }

    activeWeaponItems.Clear();
    List<Item> items = inventorySystem.Grid.GetUniqueItems();
    int activatedCount = 0;

    foreach (var item in items)
    {
        foreach (var weapon in weaponSlots)
        {
            if (weapon == null) continue;
            if (activatedCount >= activeWeaponLimit) break;
            if (item.Tag != weapon.Tag) continue;
            if (weapon.WeaponObject == null) continue;

            weapon.WeaponObject.SetActive(true);
            activatedCount++;
            activeWeaponItems.Add(item);
            break;
        }
    }
}
```

这里用“全关再开”的方式，是因为背包是一个低频变化系统。比起维护复杂差量状态，当前 Demo 更需要逻辑确定、bug 面小、容易 review。

### 唯一物品列表：顺序就是玩法

```csharp
public List<Item> GetUniqueItems()
{
    List<Item> placedItems = new List<Item>();
    HashSet<Item> itemSet = new HashSet<Item>();

    for (int y = 0; y < Height; y++)
    {
        for (int x = 0; x < Width; x++)
        {
            if (cells[x, y] == null) continue;

            Item item = cells[x, y];
            if (itemSet.Contains(item)) continue;

            itemSet.Add(item);
            placedItems.Add(item);
        }
    }

    return placedItems;
}
```

外层 `y`、内层 `x` 的遍历顺序，就是“从上到下、从左到右”。这不是偶然实现细节，而是本课确立的玩法契约：背包左上区域拥有更高激活优先级。

### UI 激活标记：查具体实例

```csharp
itemView.SetActiveWeapon(backpackWeaponActivator.IsWeaponItemActive(item));
```

如果这里只查 `ItemTag.Pistol`，两把手枪都会亮；查 `Item` 实例，才能做到只有真正被激活的那一把亮。玩法上限为 1 时，这个差异非常关键。

### 拖拽重绘补偿：攒一次，落地后补

```csharp
private void Redraw()
{
    if (isDragging)
    {
        needsRedrawAfterDrag = true;
        return;
    }

    needsRedrawAfterDrag = false;
    // 后续执行全量重绘
}
```

```csharp
dragItem = null;
ghost = null;

if (needsRedrawAfterDrag)
{
    Redraw();
}
```

这个补偿只放在“不会自然 Place 并触发 OnChanged 的结局”里。正常放置仍然交给 `InventoryGrid.Place()` 的 `OnChanged` 驱动，避免一件事被画两遍。

### 覆盖层自适应：尺寸来自 step

```csharp
public void UpdateOverlayLayout(float step)
{
    float connectorSize = Mathf.Clamp(step * 0.16f, 10f, 14f);
    float activeMarkerSize = Mathf.Clamp(step * 0.28f, 18f, 24f);
    float inset = Mathf.Clamp(step * 0.1f, 6f, 8f);

    LayoutImage(topConnector, new Vector2(0.5f, 1), new Vector2(0, -inset), connectorSize);
    LayoutImage(rightConnector, new Vector2(1, 0.5f), new Vector2(-inset, 0), connectorSize);
    LayoutImage(bottomConnector, new Vector2(0.5f, 0), new Vector2(0, inset), connectorSize);
    LayoutImage(leftConnector, new Vector2(0, 0.5f), new Vector2(inset, 0), connectorSize);
    LayoutImage(activeWeaponUI, new Vector2(0, 1), new Vector2(inset, -inset), activeMarkerSize);
}
```

表现层不要假设所有物品都是 1×1。背包游戏里，物品尺寸本身就是玩法信息，所以覆盖层必须跟着物品尺寸走。

## 三、周期链路

### 物品进入背包后的激活链路

```text
DropItem / LootChest / Discard 回收路径
        ↓
InventorySystem.HandleCollected()
        ↓
InventoryGrid.Place()
        ↓
InventoryGrid.OnChanged
        ↓
BackpackWeaponActivator.RefreshActiveWeapons()
        ↓
关闭全部武器 → 按背包左上优先重新激活
        ↓
InventoryUIController.Redraw()
        ↓
ItemView.SetActiveWeapon()
```

### 拖拽丢弃后的修复链路

```text
BeginDrag
  ↓
grid.Remove(item)
  ↓
OnChanged 触发 Redraw
  ↓
isDragging == true，Redraw 不画，只记录 needsRedrawAfterDrag
  ↓
EndDrag 面板外丢弃 / 合并 / 满包丢弃
  ↓
清理 dragItem 和 ghost
  ↓
needsRedrawAfterDrag == true 时补一次 Redraw
```

这条链路的本质是：拖拽期间 UI 不能被全量刷新打断，但拖拽结束后不能漏掉那次数据变化。门闸和补偿必须成对出现。

### 旋转 ghost 的表现链路

```text
HandleRotate()
  ↓
Item.Rotate()
  ↓
ghost.sizeDelta 按 Width / Height 重新设置
  ↓
CanPlaceAt 或 CanMerge 重新判定红绿
  ↓
UpdateOverlayLayout(step) 重排接口点和激活角标
```

为什么旋转也要更新覆盖层？因为接口点和角标挂在 `ItemView` 尺寸上，尺寸变了，视觉锚点不刷新就会出现“看起来没贴边”的问题。

## 四、设计思考

### 1. 为什么默认自动武器上限先定为 1？

因为上限为 1 时，背包位置才立刻有意义：玩家必须决定“我现在真正带哪把武器输出”。如果一开始所有武器都能同时激活，背包摆放就只剩整理空间，少了战斗选择。

上限为 1 还给 DualWield 留出了清晰价值：双持不是简单加一点数值，而是能突破默认激活规则，让第二把相邻手枪也进入战斗。这种收益一眼可见，适合 Demo。

### 2. 为什么优先级交给背包位置，而不是 Inspector Priority？

Inspector Priority 对开发者方便，但对玩家不可见。玩家看不到 `priority = 10`，也就无法学习和利用规则。

背包左上优先则完全可见、可操作、可解释。玩家移动物品后立刻看到激活标记变化，这就是把系统规则转成可玩的交互。

### 3. 为什么记录激活的 Item，而不是 ItemTag？

`ItemTag` 表达“种类”，`Item` 表达“这一件具体物品”。当背包里有三把手枪时，三者 Tag 都是 `Pistol`，但激活的只应该是其中一把。

所以 UI 标记必须查 `HashSet<Item>`。这是对象身份和类别标签的边界：类别用于匹配，实例用于裁决。

### 4. 为什么本课不做真实冷却遮罩？

真实冷却遮罩需要战斗武器向背包 UI 回传冷却进度，这会牵涉武器状态暴露、UI 订阅、生命周期、拖拽重绘和多武器映射。它当然重要，但不是“15 分钟 Demo 是否成立”的第一关键。

本课先做激活标记，玩家已经能理解“背包物品影响战斗实体”。冷却遮罩后移，避免在 Demo 冲刺期过早扩大战斗 UI 状态同步复杂度。

### 5. 为什么拖拽重绘 bug 很有代表性？

因为它暴露的是 UI 系统常见矛盾：数据变化需要立刻广播，但拖拽中的表现对象又不能被刷新销毁。

正确解法不是强行让 `Redraw()` 无脑执行，而是承认拖拽期间存在“UI 临时态”，用门闸保护它，再用补偿机制补上期间漏掉的重绘。这是事件驱动 UI 里非常实用的思路。

## 五、踩坑记录

### 坑 1 · 被丢掉的激活武器不会立刻让下一把亮起来

- **现象**：拖拽丢掉带激活标记的武器后，玩家身边的武器实体能正确切换，但背包内新激活物品的角标不立刻出现。
- **原因**：`BeginDrag()` 期间 `grid.Remove()` 触发了 `OnChanged`，但 `Redraw()` 因为 `isDragging` 被拦住；拖拽结束如果没有 `Place()`，就没有第二次自然重绘。
- **修复**：新增 `needsRedrawAfterDrag`，拖拽期间记录“漏过一次重绘”，在非 Place 结局清理拖拽状态后补画。
- **为什么不是简单 EndDrag 开头 Redraw**：那会在 `dragItem/ghost` 还没清理时刷新，容易制造更乱的生命周期问题。

### 坑 2 · 只按 Tag 标记会让同类武器全亮

- **现象预判**：若记录 `ItemTag.Pistol`，背包内所有手枪都会显示激活。
- **根因**：Tag 是类别，不是实例身份。
- **修复**：用 `HashSet<Item>` 记录当前激活实例。
- **经验**：当系统里出现“同类多个对象但只有一个生效”时，优先问自己：我现在需要类别，还是需要实例？

### 坑 3 · 场景里的测试上限容易和课程目标冲突

- **现象**：场景 Inspector 曾出现 `activeWeaponLimit = 3`，但课程和计划目标是默认上限 `1`。
- **风险**：测试方便会悄悄改掉玩法规则，让后续 DualWield 的价值被吃掉。
- **修复**：提交前确认场景值回到 `1`。
- **经验**：Demo 冲刺期尤其要区分“为了测试临时打开”和“玩法规则真的改变”。

### 坑 4 · 接口点尺寸不跟物品尺寸走，会显得廉价

- **现象**：接口点和激活 UI 如果只在 prefab 里固定位置，1×1 看着还行，2×1、1×2、旋转后就不贴边。
- **原因**：覆盖层没有把 `ItemView` 的实际尺寸当输入。
- **修复**：`Bind()` 和旋转后调用 `UpdateOverlayLayout(step)`，统一按 step、inset、anchor 重排。
- **经验**：背包 UI 里“贴边、贴角、跟随尺寸”不是小美术问题，它直接影响玩家是否相信这个系统。

## 六、面试问答

**Q1：你怎么把背包里的物品和玩家身边的武器实体关联起来？**
> 我做了一个 `BackpackWeaponActivator`，监听背包网格的 `OnChanged`。每次背包变化时，先关闭所有武器实体，再按背包里物品的顺序重新匹配 `ItemTag -> WeaponObject`。这样逻辑简单、确定，而且背包变化频率低，全量重算成本可以接受。

**Q2：为什么激活顺序用背包位置，而不是给武器配一个 priority 字段？**
> 因为背包位置对玩家可见、可操作。左上优先能让玩家通过整理背包决定当前激活武器，规则不需要额外 UI 教学。`priority` 字段更像开发者配置，玩家看不到，也不容易形成玩法。

**Q3：为什么 UI 激活标记要记录 Item 实例，而不是 ItemTag？**
> 因为 `ItemTag` 只能说明物品种类，比如都是手枪；但上限为 1 时，真正激活的是某一把具体手枪。用 `HashSet<Item>` 存实例，UI 才能只给被激活的那一件物品打标。

**Q4：你怎么处理拖拽期间背包变化导致 UI 重绘的问题？**
> 拖拽期间 `Redraw()` 不直接执行，而是设置 `needsRedrawAfterDrag`。等拖拽结束、`dragItem` 和 `ghost` 清理后，如果这次操作不会自然触发新的 `Place()`，就补一次 `Redraw()`。这样既保护拖拽中的 ghost，又不漏掉背包变化。

**Q5：为什么 `RefreshActiveWeapons()` 里先关闭所有武器再重新打开？这会不会浪费？**
> 对当前背包系统来说，变化频率很低，武器数量也很少。全量重算牺牲一点点性能，换来状态确定和实现简单。等未来武器数量、状态复杂度上来，再考虑差量更新更合适。

**Q6：为什么真实冷却遮罩没在这一课做？**
> 冷却遮罩不是单纯 UI 图片，它需要武器运行状态和背包物品实例之间持续同步。Demo 冲刺阶段，先做激活标记就能完成“背包影响战斗”的核心表达；冷却同步复杂度高、收益延后，所以后移到 P2。

**Q7：如果以后 DualWield 要让第二把手枪也激活，你准备怎么接？**
> 当前默认上限为 1，`ScanAdjacency` 已经能返回 DualWield 候选效果。后续可以在效果结算器里判断每把武器最多参与一组 DualWield，然后把通过结算的第二把武器加入激活名单，或者临时提高特定 Tag 的激活上限。

## 八、思考题（附复习参考）

**Q1：为什么 `GetUniqueItems()` 需要 `HashSet<Item>`？**
> 因为一个 2×2 物品会占据多个格子，二维数组里四个格子都指向同一个 `Item` 实例。如果不用 HashSet 去重，同一件物品会被加入多次，可能重复激活或挤占激活上限。

**Q2：为什么 `GetUniqueItems()` 的遍历顺序可以成为玩法规则？**
> 因为它是稳定、可解释、可被玩家控制的顺序：外层 y、内层 x，就等于从上到下、从左到右。只要我们把这个顺序写成注释和课程约定，它就不再只是实现细节，而是背包优先级规则。

**Q3：如果未来要做“玩家手动选择激活武器”，现在的系统要推翻吗？**
> 不需要。可以把位置优先当默认排序，再加一个玩家 pin/lock 机制。`BackpackWeaponActivator` 仍然负责消费一个候选列表，只是候选列表的排序规则从“纯位置”扩展成“手动选择优先，其次位置”。

**Q4：为什么拖拽期间不直接允许 `Redraw()`？**
> 因为 `Redraw()` 会销毁并重建 `itemLayer` 的所有子物体，而 ghost 本身就是其中一个 `ItemView`。拖拽中直接重绘会把手上的对象生命周期打乱。门闸让拖拽表现保持稳定，补偿重绘保证数据变化最终反映出来。

**Q5：`activeWeaponLimit = 1` 和 DualWield 是什么关系？**
> `activeWeaponLimit = 1` 建立默认约束：普通情况下只能激活一把武器。DualWield 的价值就是在满足邻接条件时突破这个默认约束。没有约束，就没有构筑收益的对比。

**Q6：为什么真实冷却遮罩比激活标记复杂？**
> 激活标记是离散状态：开或关；冷却遮罩是连续状态：每帧或每次攻击周期都要同步百分比。它还需要知道“这个 Item 对应哪把正在运行的 WeaponObject”，所以必须等武器状态暴露和映射关系更稳定后再做。
