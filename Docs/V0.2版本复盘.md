## 三、版本系统总览

### 1. 战斗与伤害

V0.2 延续 V0.1 的 `IDamageable / Health / DamageInfo / WeaponBase` 管线，并进一步把战斗收益接入背包构筑。

最终伤害不再只是武器 prefab 的固定数值，而是由多层来源共同决定：

```text
武器基础伤害
  × PlayerRunStats 玩家升级倍率
  × WeaponItemStatResolver 背包武器稀有度/等级倍率
  × DamageBoost 攻击芯片倍率
```

这条链路让“背包中具体放了什么武器、武器是什么品质、有没有邻接芯片”真实影响战斗，而不是只停留在 UI 展示。

### 2. 掉落、宝箱与经济

掉落系统从最初的单次权重随机，升级为多频道搜刮系统：

```text
LootTableData / LootRoller / LootManager
  -> XpOrb / GoldOrb / DropItem / LootChest
  -> 磁吸拾取 / E 键交互 / 宝箱奖励 / 背包入库
```

经验和金币走磁吸，装备走近身交互，宝箱复用 `IInteractable`。这让“货币快速吸收、装备需要主动选择”的体验更接近搜刮类游戏节奏。

### 3. 纯 C# 背包内核

背包核心由 `BS.Inventory` 独立程序集承载，不引用 `UnityEngine`。`InventoryGrid` 负责真实规则：

```text
CanPlaceAt / Place / Remove / TryFindFreeArea / TryMerge
ScanAdjacency / GetUniqueItems / GetTotalScoreValue
```

UI 不直接拥有规则，只是监听数据变化后投影。这是 V0.2 最有工程价值的一条线，因为它把 Gameplay 规则从 UGUI 拖拽细节里隔离出来。

### 4. 背包 UI 与交互

背包 UI 支持完整的玩家操作：拖拽、红绿预览、冲突检测、旋转、合并、丢弃、重新拾取、Tooltip、Tab 开关和物品图标显示。

V0.2 期间多次修正了拖拽边界问题，最终形成了一个重要规则：**数据安全优先于手感表现**。任何拖拽分支都必须保证物品不会丢失，即使放置失败，也要回滚、找空位或继续手持。

### 5. 邻接构筑与规则解析

邻接系统没有写成散落在 UI 或武器逻辑里的 if-else，而是拆成：

```text
ItemTag
ConnectableSides
AdjacencyRuleBook
InventoryGrid.ScanAdjacency
AdjacencyEffectResolver
```

其中 `RuleBook` 定义候选规则，`Resolver` 判断真实有效效果。这样可以区分“看起来相邻”和“规则真正生效”，也方便未来扩展更多芯片、互斥和层数策略。

### 6. 单局框架与波次导演

`GameSession / RunTimer / GameState / RunResult` 形成单局框架，`WaveDirector` 负责把时间推进转换成刷怪压力、敌人血量、精英概率和宝箱品质变化。

这让 V0.2 从“能打怪”变成“有一局游戏的节奏”：前期建立构筑，中期搜刮宝箱，后期压力提高，玩家需要在战斗和整理背包之间做取舍。

### 7. 表现、反馈与包装

V0.2 后半段集中补齐了玩家能直接感受到的反馈：

- 命中闪白、受击闪红。
- 池化伤害数字。
- 开火、命中、拾取、升级、开箱、受伤音效。
- 轻量相机震动。
- 物品图标、稀有度底色、等级星星、邻接接边。
- 主菜单、玩法说明、制作者声明、结算页。

这些内容的技术难度不一定最高，但对 Demo 观感价值很大。V0.2 的一个重要认知是：**Demo 冲刺期必须优先补“一眼能看见”的体验面。**

## 四、架构沉淀

### 1. Model 与表现层解耦

背包系统不是严格教科书 MVC，但具备清晰的 MVC 分层思想：

```text
Model：InventoryGrid / Item / AdjacencyRule / AdjacencyEffect
View：ItemView / ItemTooltipView / 背包格子 / 接边 / 激活角标
Controller/Presenter：InventoryUIController
Gameplay Adapter：InventorySystem / BackpackWeaponActivator
```

更准确的描述是：**纯数据 Model + UI 投影 + Gameplay 适配器**。

这比直接说“用了 MVC”更稳，因为 Unity Gameplay 里往往不是纯 UI 架构，很多系统会从 Model 订阅状态并影响另一个 Gameplay 系统。

### 2. 事件驱动的系统协作

V0.2 中大量系统通过事件连接：

```text
Health.OnDeath -> 掉落、击杀统计
InventoryGrid.OnChanged -> UI 重绘、武器激活、价值刷新
XpOrb.OnCollected / GoldOrb.OnCollected -> GameSession 统计
GameSession.OnStateChanged / OnRunEnded -> HUD / ResultView
WaveDirector.OnWaveStageChanged -> HUD 文案与颜色
```

事件让系统之间不必互相硬引用全部细节，但也带来了镜像订阅、生命周期和重复触发问题。V0.2 的多个 Bug 都来自这里，因此最终沉淀出规则：**Awake 拿自身引用，OnEnable 订阅，OnDisable 退订，Start 再拿外部引用。**

### 3. 对象池生命周期

对象池从 V0.1 的敌人/子弹扩展到 V0.2 的经验、金币、装备、宝箱和伤害数字。池化的收益是减少高频 Instantiate/Destroy，但真正复杂的是复用状态：

```text
出池：重置运行期字段、状态机、协程、碰撞器、显示状态
服役：执行当前生命周期逻辑
回池：幂等归还，避免重复回收
复用：不能带着前世状态进入新生命周期
```

因此本阶段形成了一条机械规则：**池化类新增运行期字段，同一分钟检查并写入 OnGetFromPool 归零逻辑。**

### 4. Demo 冲刺期的优先级管理

7 月 28 日后，项目目标从“深入系统”切换为“8 月 15 日前完成 15 分钟可试玩 Demo + 求职材料”。这次重排很关键。

V0.2 没有继续深挖完整 Gold 商店、撤离经济、复杂 Boss、网络、动画系统，而是优先补：

```text
单局闭环
构筑影响战斗
金币与价值反馈
波次压力
主菜单与玩法说明
表现与音效
Profiler 快扫
正式 Build
Release 与 README
```

这个取舍让项目没有无限扩张，而是在 3 周内形成一个能被别人试玩、理解和评估的版本。

## 六、性能与取舍复盘

V0.2 的性能策略不是“见到理论优化就做”，而是按规模和风险取舍。

### 已做的优化

- `sqrMagnitude` 替代 `magnitude`：用于掉落物磁吸距离判断，避免每帧开方。
- `SphereCastNonAlloc`：用于子弹扫掠检测，减少物理查询分配。
- 对象池：覆盖敌人、子弹、经验、金币、装备、宝箱和伤害数字。
- ItemView 参数注入：避免每个视图生成时 `FindAnyObjectByType` 全场景查找。
- 显式材质 + `MaterialPropertyBlock`：修复 Build 颜色异常，同时避免为每个对象频繁实例化材质。

### 明确不做的优化

- `InventoryGrid.Contains` 不上 HashSet：6×8 背包只有 48 格，全扫描足够快；HashSet 会引入冗余状态同步成本。
- 背包 UI 不做局部刷新：48 格全量重绘足够稳定，局部刷新需要脏标记和差异追踪，复杂度高于收益。
- Profiler 快扫后不做大重构：Editor 尖刺主要来自 EditorLoop / Live Display / 资源上传观察成本，正式 Build 后期波次没有明显卡顿。

V0.2 最重要的性能认知是：**性能优化先判断瓶颈属于哪里，再决定是否改代码。** 如果问题只在 Editor/Profiler 观察环境中出现，而正式 Build 不复现，就不应该在 Demo 冻结期大重构。

## 七、玩家体验复盘

### 做得有效的体验点

1. **宝箱距离提示**：没有做箭头，而是显示最近宝箱距离。这样既给玩家目标，又保留自己判断路线的空间。
2. **背包 Tab 开关**：减少背包长期占屏，使战斗画面更干净，也让整理背包成为有风险的主动行为。
3. **物品图标 + 接边 + 星级**：让物品从“彩色方块”升级为更容易理解的构筑组件。
4. **玩法说明面板**：外部试玩暴露了邻接和武器激活理解门槛，说明复杂系统必须配最短引导。
5. **终局压力**：用户试玩中出现“高价值背包但整理时被偷袭失败”，证明战斗压力和背包整理之间已经有张力。

### 仍然不足的体验点

1. **新手引导仍偏静态**：目前主要靠主菜单玩法说明，局内动态目标提示还不够。
2. **构筑收益缺少集中展示**：玩家能看到金色接边，但不一定清楚当前总共获得了多少攻速/伤害收益。
3. **金币经济只到 HUD**：金币已经掉落和统计，但商店、出售、撤离等更深经济闭环仍是 Demo 后内容。
4. **危险区表现暂缓**：V0.1 有 HazardZone 逻辑，但 v0.2 正式包装中暂未做危险区美术和终局压缩。
5. **内容量仍是 Demo 级**：三类武器、两类芯片和几类物品足够展示系统，但距离完整商业内容还很远。

## 九、版本不足与风险

### 1. 系统深度不足

当前邻接系统已经有双持、攻速芯片和攻击芯片，但还没有暴击、燃烧、防具、护盾、范围、冷却等更多构筑维度。系统框架已经留出扩展空间，内容深度仍需要后续填充。

### 2. 配置数据化不完全

部分数值和规则仍然依赖场景或脚本字段配置。后续如果继续扩内容，应该把物品、规则、权重、波次和芯片效果进一步 ScriptableObject 数据化。

### 3. 教学/复盘文档较多

公开仓库保留了课程总结、Bug 记录和性能记录，用于展示开发过程；但内部导师手册、交接提示词、简历准备材料和本地视频已通过 `.gitignore` 保留在本地，不进入公开仓库。这是作品展示和个人准备之间的边界取舍。

### 4. 资源授权仍需谨慎

v0.2 使用的部分美术、字体、音效、模型或占位资源仅用于 Demo 展示和学习验证。若未来商业化或继续扩大传播，需要逐项确认授权或替换为自制/可商用资源。

## 十、进入 V0.3 的方向

V0.3 不建议立刻无脑加内容，而应该围绕“让构筑更可读、更有决策、更能形成循环”推进。

优先级建议：

```text
P0：作品材料收尾，确保 README / Release / 视频 / 简历表达一致
P1：局内构筑收益展示、第二类芯片、更多武器差异、金币结算页
P2：物品与规则 ScriptableObject 数据化、Gold 商店、出售/撤离经济
P3：完整 Boss 机制、危险区表现强化、附近战利品面板、更多音效混音
P4：网络、复杂动画、RPG 动作项目等另开新项目专题
```

如果目标是求职，V0.2 已经足够作为“第一款完整可试玩作品”；V0.3 应该服务于面试表达和作品补强，而不是把项目拖成无限扩张的长期坑。

## 十一、阶段总结

V0.2 的核心价值可以概括为一句话：

> 把一个战斗原型推进成了可以独立运行、可以被别人试玩、可以用于求职展示的完整 Demo。

这个阶段最重要的成长不是多写了多少功能，而是建立了从玩法目标到工程落地的完整方法：

```text
先做核心规则
  -> 再接 UI 和反馈
  -> 再接战斗/经济/结算闭环
  -> 再做数值和可读性
  -> 最后做 Profiler、Build、Release 和展示材料
```

V0.2 也证明了一件事：对于个人独立项目，最难的不是想到一个系统，而是持续做正确取舍，把系统串成一条别人能实际体验到的闭环。
