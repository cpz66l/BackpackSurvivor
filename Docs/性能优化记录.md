# 《背包幸存者》性能优化记录

> 用途：记录性能优化决策——**做过什么优化，以及同样重要的：为什么不做某个优化**。
> 维护规则：每次做性能相关的权衡或修改，按模板追加，编号递增。
> 面试话术核心：性能题的满分答案不是"我用了某技术"，而是"**瓶颈在哪、我怎么判断的、收益和成本各是什么**"。

## 记录模板

```
### OPT-XXX · 标题
- 日期 / 所属系统：
- 瓶颈/隐患：
- 方案：
- 效果：
- 决策依据（为什么做/为什么不做）：
```

## OPT-001 · ItemView 每次生成做一次全场景查找

- **日期**：2026-07-25 · **所属系统**：背包 UI（ItemView / InventoryUIController）
- **瓶颈/隐患**：ItemView 的 Start 里 `FindAnyObjectByType<InventoryUIController>()`——每次重绘生成 N 个视图 = N 次全场景搜索，背包越满重绘越卡，典型的"n 个小开销叠成帧尖刺"
- **方案**：改为参数注入——`Bind(item, step, controller)`，由控制器在 Instantiate 后把自己传进去；删除 Start。零搜索
- **效果**：重绘从 N 次场景扫描降为 0 次；同时消除"视图生成当帧被秒点导致 controller 为 null"的时序边角
- **决策依据**：Find* 系列是运行时搜索，能只在初始化做一次就绝不放热点路径；而"父传子"的注入本来就是这个依赖关系最自然的形态——**性能优化和代码结构优化经常是同一刀**

## 历史精选（补录）

### OPT-000A · 距离判断用 sqrMagnitude 替代 magnitude
- **系统**：PickUpMagnet 磁吸状态机
- **瓶颈**：magnitude 内部有开方运算，每帧 × 全场掉落物
- **方案**：比较平方距离（sqrMagnitude）与半径平方，省掉开方
- **决策依据**：Unity 性能肌肉记忆：比较距离永远比平方，开方只在需要真实距离值时用（如移动归一化）

### OPT-000B · 对象池消除 Instantiate/Destroy 的 GC 峰值
- **系统**：敌人 / 子弹 / 掉落物
- **瓶颈**：幸存者类游戏同屏几十上百个短寿命对象，频繁 Instantiate/Destroy 造成 GC 峰值卡顿
- **方案**：ObjectPool + IPoolable：Queue 存闲对象、SetPool 车票认池、Get/Return 循环服役；预热 + 弹性扩容
- **决策依据**：高频短寿命对象必池化；扩容对象首还入籍防泄漏

### OPT-000C · 子弹碰撞用 SphereCastNonAlloc
- **系统**：Projectile 扫掠检测
- **瓶颈**：Physics 分配的数组版本每次调用产生 GC 垃圾，子弹每秒几十次调用
- **方案**：NonAlloc 版本 + 复用预分配缓冲区；扫掠防穿透（高速物体帧间跳过薄墙）
- **决策依据**：FixedUpdate/Update 热点路径上零容忍 GC 分配

### OPT-000D · ★ 决定"不做"HashSet 优化（反向案例）
- **系统**：背包 InventoryGrid.Contains
- **背景**：Contains 全扫描 O(n)，理论可优化为 HashSet O(1)
- **为什么不**：6×8=48 格全扫描本就飞快，无体感瓶颈；引入 HashSet = 引入冗余状态，每条写入路径都背上同步契约，维护成本 > 收益
- **决策依据**：**先问渐近成本的实际体感，再算冗余状态的维护账**。没有测量支撑的优化是过度设计；这条决策本身就是面试答案——"知道什么时候不优化，和知道怎么优化一样重要"

### OPT-000E · 玩家引用缓存而非每帧查找
- **系统**：EnemyAI / PickUpMagnet
- **瓶颈**：FindGameObjectWithTag 每帧 × 每个敌人 = 每秒数千次全场景遍历
- **方案**：初始化时查一次缓存起来（Transform + Health 双缓存，顺便拿受击点坐标和死亡状态）
- **决策依据**：不变或慢变的引用，查找前移；热点路径只留纯计算

### OPT-000F · 背包 UI 全量重绘而非局部刷新（反向案例）
- **系统**：背包 UI
- **背景**：OnChanged 后"只更新变化的格子"理论上更省
- **为什么不**：48 格全量重建毫无压力；局部刷新需要脏标记+差异追踪，代码复杂度翻倍还容易漏刷。全量重绘还白得一个福利：颜色、状态永不残留（预览色无需手动复位）
- **决策依据**：优化先量化。帧预算内无压力的路径，简单性 > 理论效率；量级变化（格子×100）时再回头评估

## OPT-002 · Profiler 快扫后决定不做大重构

- **日期**：2026-08-08 · **所属系统**：Demo 打包前性能闸门（Unity Profiler / Build 验证）
- **瓶颈/隐患**：Editor 试玩后期有“几秒一顿”的体感，Profiler 中也能看到 200ms 甚至 1000ms 级别尖刺，表面上像是后期波次或对象数量导致卡顿。
- **方案**：用 Profiler Timeline / Hierarchy 区分耗时来源：一次尖刺落在 `EarlyUpdate.UpdatePreloading` / `Application.WaitForAsyncOperationToComplete` / `Gfx.UploadTexture`，更像资源预加载和纹理上传；另一次尖刺 `EditorLoop` 占 99.2%，`PlayerLoop` 仅约 1.30ms，属于 Editor/Profiler Live display 观察开销。随后用 Build 实测后期波次，确认没有明显掉帧，不对 EnemyAI、Projectile、InventoryUI 做大重构。
- **效果**：避免在打包前夕误把 Editor/Profiler 开销当作游戏逻辑瓶颈，保住 Demo 冲刺节奏；同时把关键截图整理到 `Docs/ProfilerEvidence/`，作为简历/面试中的性能分析证据。
- **决策依据**：性能优化先定性再定量，先问“耗时属于哪个线程/模块/运行环境”，再决定是否改代码。Build 无复现的 Editor 尖刺，不值得在 Demo 冻结期做大重构。

## OPT-003 · PickUpMagnet 每个掉落物订阅背包变化的性能隐患

- **日期**：2026-08-16 · **所属系统**：拾取磁吸 / 背包被动效果（PickUpMagnet / BackpackPassiveCollector）
- **瓶颈/隐患**：当前每个带 `PickUpMagnet` 的掉落物都会在启用时订阅 `InventoryGrid.OnChanged`，背包变化后各自调用 `BackpackPassiveCollector.Collect(Grid.GetUniqueItems())` 刷新磁吸范围加成。Demo 当前掉落物数量不大，体感和测试都没问题；但如果后续同屏掉落物明显增多，玩家整理背包时可能出现 N 个掉落物同时重复汇总背包被动的瞬时开销。
- **方案**：当前不立即重构，保留每个掉落物本地缓存背包被动结果；后续如果 Profiler 证明背包整理时出现尖刺，再把背包被动汇总集中到共享服务，例如 `BackpackPassiveRuntime`，由它订阅一次背包变化并缓存 `BackpackGlobalModifier`，`PickUpMagnet` 只读取共享结果。
- **效果**：保持 v0.3.3 实装简单，避免为了尚未出现的瓶颈引入全局服务；同时提前记录风险，后续一旦掉落密度提高，可以快速定位优化方向。
- **决策依据**：性能优化要看频率和量级。`PickUpMagnet.Update()` 是高频路径，所以距离计算继续保持轻量；`OnChanged` 是低频背包事件，当前重复汇总可接受。真正需要警惕的是“低频事件 × 大量订阅者”在规模上来后的尖刺。
