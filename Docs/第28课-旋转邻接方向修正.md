# 第28课 · 旋转邻接方向修正

> 课程周期：2026-08-04  
> 前置：第27课《数值调参台与首轮平衡》  
> 关键词：RotationState、本地方向、世界方向、邻接规则、正反向匹配、UI 投影一致性

---

## 一、这节课实现了什么

第28课把“物品旋转”从只影响宽高，推进到真正影响邻接接口方向。  
现在背包里一个物品按 R 旋转后，它的灰色接口点、金色生效边、`ScanAdjacency()` 返回结果和真实战斗效果都会跟着旋转后的方向走。

这节课的核心不是 UI，而是规则语义：  
**规则表写的是物品自己的本地方向，背包扫描看到的是当前摆放后的世界方向。**

### 任务 1 · bool Rotated 升级为四状态 RotationState

- `Item` 不再只保存 `bool Rotated`。
- 新增 `RotationState`，支持 0° / 90° / 180° / 270° 四个状态。
- `Rotate()` 每次顺时针旋转 90°。
- `Width / Height` 根据 `RotationState` 决定是否互换。
- `BaseWidth / BaseHeight` 暴露原始尺寸，给丢弃还原使用。

这一步解决了“接口可以旋转 360 度”的表达问题。  
如果仍然用 bool，只能表达“转了 / 没转”，无法区分 90° 和 270°。

### 任务 2 · 建立本地方向到世界方向的统一转换

- `LocalConnectableSides` 继续表示物品原始朝向下的接口。
- 新增 `GetWorldSides(localSides)`，把本地方向按当前 `RotationState` 转成世界方向。
- `GetWorldConnectableSides()` 改为 `GetWorldSides(LocalConnectableSides)`。

现在方向事实源集中在 `Item`：  
UI 不猜方向，邻接扫描也不猜方向，都问 `Item` 当前世界接口是什么。

### 任务 3 · 修正 ScanAdjacency 的规则匹配

- `ScanAdjacency()` 仍然只扫描右边和下边，避免重复扫描。
- `TryMatchNeighbor()` 先用 `GetWorldConnectableSides()` 做接口存在性检查。
- 遍历规则时，新增 `forwardMatched / reverseMatched` 两套匹配。
- 匹配时把 `rule.SideA / rule.SideB` 从本地方向转换成对应物品的世界方向。

这一步修掉了本课最关键的问题：  
不能把 `rule.SideA` 和 `sideA` 直接比较，因为一个是本地方向，一个是世界方向。

### 任务 4 · 保证 Tag 和 Side 成对绑定

初版正反向匹配把 Tag 和 Side 拆散了，导致规则可能出现这样的错误：

```text
rule.TagA 对上了 Rifle
但 rule.SideA 却被拿去套 Magazine
```

最终修正为：

```text
正向：rule.TagA + rule.SideA 同时绑定 itemA
反向：rule.TagA + rule.SideA 同时绑定 itemB
```

也就是说，`TagA` 和 `SideA` 永远属于同一个规则物品，`TagB` 和 `SideB` 同理。

### 任务 5 · 拖拽中旋转即时刷新接口点

- `InventoryUIController.HandleRotate()` 中，旋转后会刷新 ghost 尺寸。
- 同步调用 `SetConnectors()` 刷新灰色接口点。
- 拖拽中 `activeSides` 先给 `None`，避免手持物品显示假金边。
- 放下后由 `Redraw()` 重新计算真实 `validEffects`。

这样玩家按 R 时，接口点会立刻跟着转，不必等松手后重绘。

### 任务 6 · 丢弃路径恢复原始朝向

- `DiscardToWorld()` 还原 `LootEntry` 时改用 `item.BaseWidth / item.BaseHeight`。
- `connectableSides` 继续写 `item.LocalConnectableSides`。
- 当前 Demo 取舍：旋转后的物品丢出再捡回，会恢复原始朝向。

这比“宽高是旋转后的，接口却是原始的”更自洽，也避免运行时旋转状态污染静态掉落数据。

### 任务 7 · 最终验收通过

本课已通过 Unity 内测：

- 单物品接口随 R 键按 `Up → Right → Down → Left → Up` 循环。
- 原始可触发的邻接规则仍然触发。
- 原来不能触发的布局，旋转后可以触发。
- 规则表写 `Rifle + Magazine`，实际摆成 `Magazine + Rifle`，旋转后仍能触发。
- UI 灰点、金点和真实效果一致。

## 二、最终代码（关键片段）

### 1. RotationState 表达四种旋转状态

```csharp
public Rotation RotationState { get; private set; }

public enum Rotation
{
    None,
    Clockwise90,
    Clockwise180,
    Clockwise270
}
```

`RotationState` 不是显示用字段，而是背包规则层的真实状态。  
宽高、接口方向、自动找位和邻接匹配都会读它。

### 2. 宽高根据旋转状态换算

```csharp
public int Width
{
    get
    {
        if (RotationState == Rotation.None || RotationState == Rotation.Clockwise180)
            return baseWidth;
        else
            return baseHeight;
    }
}

public int Height
{
    get
    {
        if (RotationState == Rotation.None || RotationState == Rotation.Clockwise180)
            return baseHeight;
        else
            return baseWidth;
    }
}
```

0° 和 180° 不互换宽高，90° 和 270° 互换宽高。  
这是旋转物品在格子背包里的基础几何规则。

### 3. Rotate() 顺时针循环

```csharp
public void Rotate()
{ 
    if (RotationState == Rotation.Clockwise270)
        RotationState = Rotation.None;
    else
        RotationState++;
}
```

当前实现依赖 enum 顺序，Demo 期可接受。  
后续如果想更稳，可以改成 switch 或 `(int + 1) % 4`。

### 4. 本地方向转世界方向

```csharp
public ConnectableSides GetWorldConnectableSides()
{
    return GetWorldSides(LocalConnectableSides);
}

// 把本地方向按当前 RotationState 转成世界方向
public ConnectableSides GetWorldSides(ConnectableSides localSides)
{
    ConnectableSides worldSides = ConnectableSides.None;

    if (RotationState == Rotation.None)
        worldSides = localSides;
    else if (RotationState == Rotation.Clockwise90)
    {
        if ((localSides & ConnectableSides.Up) != 0)
            worldSides |= ConnectableSides.Right;
        if ((localSides & ConnectableSides.Right) != 0)
            worldSides |= ConnectableSides.Down;
        if ((localSides & ConnectableSides.Down) != 0)
            worldSides |= ConnectableSides.Left;
        if ((localSides & ConnectableSides.Left) != 0)
            worldSides |= ConnectableSides.Up;
    }

    return worldSides;
}
```

实际代码还包含 180° 和 270°。  
重点是：`GetWorldConnectableSides()` 和规则匹配都复用同一个转换方法，不写两套方向逻辑。

### 5. TryFindFreeArea 失败后恢复调用前状态

```csharp
item.Rotate();

for (int j = 0; j < Height; j++)
{
    for (int i = 0; i < Width; i++)
    {
        if (CanPlaceAt(i, j, item))
        {
            x = i;
            y = j;
            return true;
        }
    }
}

for (int i = 0; i < 3; i++)
{
    item.Rotate();
}
```

四状态旋转后，失败回滚不能只 `Rotate()` 一次。  
从“临时多转了 90°”回到调用前状态，需要再转 270°，也就是 3 次。

### 6. 接口存在性检查读世界接口

```csharp
ConnectableSides sidesA = itemA.GetWorldConnectableSides();
ConnectableSides sidesB = itemB.GetWorldConnectableSides();

if ((sidesA & sideA) == 0) return;
if ((sidesB & sideB) == 0) return;
```

这里的 `sideA / sideB` 是扫描出来的世界接触边。  
所以必须拿物品当前世界接口去检查，而不是拿 `LocalConnectableSides`。

### 7. 正向与反向规则匹配

```csharp
bool forwardMatched =
    rule.TagA == itemA.Tag &&
    rule.TagB == itemB.Tag &&
    itemA.GetWorldSides(rule.SideA) == sideA &&
    itemB.GetWorldSides(rule.SideB) == sideB;

bool reverseMatched =
    rule.TagA == itemB.Tag &&
    rule.TagB == itemA.Tag &&
    itemB.GetWorldSides(rule.SideA) == sideB &&
    itemA.GetWorldSides(rule.SideB) == sideA;

if (!forwardMatched && !reverseMatched)
    continue;
```

这是本课最关键的代码。  
它保证 `rule.TagA + rule.SideA` 永远绑定同一个物品，不会出现 Tag 对了但 Side 套错对象的问题。

### 8. AdjacencyEffect 记录实际世界边

```csharp
AdjacencyEffect effect = new AdjacencyEffect(
    rule.EffectId,
    itemA,
    sideA,
    itemB,
    sideB);

effects.Add(effect);
```

即使是反向规则匹配成功，`AdjacencyEffect` 仍然记录扫描现场的 `itemA / sideA / itemB / sideB`。  
因为 UI 金边需要的是当前真实世界边，而不是规则表里的本地方向。

### 9. 拖拽中旋转刷新接口点

```csharp
dragItem.Rotate();

ghost.GetComponent<RectTransform>().sizeDelta =
    new Vector2(dragItem.Width * step, dragItem.Height * step);

ConnectableSides visibleSides = ghost.Item.GetWorldConnectableSides();
ConnectableSides activeSides = ConnectableSides.None;
ghost.SetConnectors(visibleSides, activeSides);
ghost.UpdateOverlayLayout(step);
```

拖拽中的 ghost 不参与真实邻接，所以只刷新灰色可连接边。  
真正金色生效边等放下后由 `Redraw()` 重新扫描。

### 10. 丢弃时恢复原始物品配置

```csharp
LootEntry entry = new LootEntry
{
    category = DropCategory.Equipment,
    id = item.Id,
    rarity = item.Rarity,
    width = item.BaseWidth,
    height = item.BaseHeight,
    amount = 1,
    itemTag = item.Tag,
    connectableSides = item.LocalConnectableSides,
    scoreValue = item.BaseScoreValue,
    effectValue = item.BaseEffectValue,
};
```

当前 Demo 不保存地面物品的旋转状态。  
所以丢弃路径统一恢复原始尺寸和原始接口，避免半旋转数据污染。

## 三、周期链路

### 旋转状态链路

```text
玩家拖拽物品按 R
  ↓
InventoryUIController.HandleRotate()
  ↓
Item.Rotate()
  ↓
RotationState 顺时针推进 90°
  ↓
Width / Height / GetWorldConnectableSides 同步变化
  ↓
ghost 尺寸与灰色接口点即时刷新
```

### 方向转换链路

```text
LocalConnectableSides
  ↓
RotationState
  ↓
Item.GetWorldSides(localSides)
  ↓
世界方向 ConnectableSides
  ↓
UI 显示 / 邻接扫描 / 规则匹配共用
```

### 邻接扫描链路

```text
InventoryGrid.ScanAdjacency()
  ↓
只扫描右边和下边
  ↓
TryMatchNeighbor(itemA, itemB, sideA, sideB)
  ↓
检查两个物品当前世界接口是否存在
  ↓
规则表本地方向转世界方向
  ↓
forwardMatched / reverseMatched
  ↓
生成 AdjacencyEffect
```

### UI 生效边链路

```text
Redraw()
  ↓
grid.ScanAdjacency()
  ↓
AdjacencyEffectResolver.ResolveValidEffects()
  ↓
GetActiveSides(item, validEffects)
  ↓
ItemView.SetConnectors(visibleSides, activeSides)
  ↓
灰色接口边 / 金色生效边统一显示世界方向
```

### 丢弃还原链路

```text
旋转后的 Item
  ↓
InventorySystem.DiscardToWorld()
  ↓
LootEntry 写 BaseWidth / BaseHeight / LocalConnectableSides
  ↓
地面 DropItem
  ↓
再次拾取 new Item(...)
  ↓
恢复原始朝向
```

## 四、设计思考

### 1. 为什么要区分本地方向和世界方向？

物品自己的设计方向和它摆进背包后的方向不是一回事。  
比如一把步枪的规则可能是：

```text
步枪本地 Down 可以接弹夹本地 Up
```

但玩家把步枪旋转 90° 后：

```text
步枪本地 Down 变成世界 Left
```

所以规则表不能直接和扫描边比较。  
规则表是本地方向，扫描边是世界方向，中间必须经过 `RotationState` 转换。

### 2. 为什么方向转换放在 Item？

因为只有 `Item` 同时知道：

```text
自己的 LocalConnectableSides
自己的 RotationState
自己的当前 Width / Height
```

如果 UI 自己转一遍，`ScanAdjacency()` 再转一遍，后续战斗效果再转一遍，就会出现三套方向事实源。  
本课的正确做法是让所有系统都问同一个对象：`Item`。

### 3. 为什么 ScanAdjacency 还只扫描右边和下边？

扫描右边和下边是为了去重。  
如果四个方向都扫，同一对物品会被扫到两次，后面还要靠更多去重逻辑兜底。

现在的结构是：

```text
扫描只负责找空间中的接触关系
正反向匹配负责解决规则表顺序问题
triggeredKeys 负责防止同一对物品重复产出同一效果
```

职责是分开的。

### 4. 为什么正反向匹配必须成套判断？

规则表里的 `TagA` 和 `SideA` 是绑定的。  
不能只判断：

```text
TagA 在这两个物品里
SideA 在这两条边里
```

这会把一个物品的标签和另一个物品的边混在一起。  
正确判断必须是：

```text
rule.TagA 对 itemA 时，rule.SideA 也必须由 itemA 转成世界边
rule.TagA 对 itemB 时，rule.SideA 也必须由 itemB 转成世界边
```

这就是 `forwardMatched / reverseMatched` 的意义。

### 5. 为什么 AdjacencyEffect 存世界边？

`AdjacencyEffect` 是运行时结果，不是配置。  
UI 金边、真实效果、激活高亮都关心“当前背包里哪条边正在生效”。

所以它应该存：

```text
实际扫描到的 itemA / sideA / itemB / sideB
```

而不是存规则表里的本地方向。  
否则 UI 还得再次把本地方向转世界方向，表现层又开始知道规则细节。

### 6. 为什么丢弃后恢复原始朝向？

当前 `LootEntry` 是静态掉落结构，它没有保存运行时旋转状态。  
如果丢弃时写当前 `Width/Height`，但又写原始 `LocalConnectableSides`，就会生成“尺寸像旋转过，接口像没旋转”的混合物品。

Demo 阶段选择更安全的取舍：

```text
丢弃后恢复原始朝向
不保存旋转态
不污染静态配置
```

正式版如果要保留地面旋转态，应该单独设计运行时掉落数据。

## 五、踩坑记录

### 1. bool Rotated 不足以表达 360 度方向

- **现象风险**：只能区分“转了 / 没转”，无法区分 90°、180°、270°。
- **根因**：bool 只适合处理宽高互换，不适合处理方向系统。
- **修复**：升级为 `RotationState` 四状态。
- **沉淀**：当需求从形状旋转进入方向规则旋转，状态表达也必须升级。

### 2. 自动找空位失败后不能只 Rotate 一次

- **现象风险**：`TryFindFreeArea()` 失败后，物品旋转状态被偷偷改变。
- **根因**：原逻辑适配 bool 旋转，四状态下多转一次不会回到原状态。
- **修复**：临时旋转 90° 后如果失败，再旋转 3 次回到调用前状态。
- **沉淀**：函数失败时必须恢复调用前状态，尤其是会临时改入参的函数。

### 3. 规则本地方向不能直接对比世界接触边

- **现象**：UI 接口点跟着旋转，但 `ScanAdjacency()` 触发结果没跟着 `RotationState` 走。
- **根因**：`rule.SideA / rule.SideB` 是本地方向，`sideA / sideB` 是世界接触边。
- **修复**：用具体物品的 `GetWorldSides(rule.SideX)` 转换后再匹配。
- **沉淀**：配置语义和运行时语义不同，中间必须有明确转换层。

### 4. 正反向匹配不能拆散 Tag 和 Side

- **现象风险**：规则 Tag 对了，但规则 Side 套到了另一个物品身上。
- **根因**：初版判断成了“TagA 在 A/B 中、SideA 在 sideA/sideB 中”，没有保持成对绑定。
- **修复**：用 `forwardMatched / reverseMatched` 两套完整绑定判断。
- **沉淀**：规则匹配时，字段之间的归属关系比单个字段是否命中更重要。

### 5. 拖拽中旋转不能等 Redraw 才更新

- **现象风险**：按 R 后真实方向已变，但 ghost 接口点仍显示旧方向。
- **根因**：拖拽期间 `Redraw()` 被门闸拦住，表现不会自动刷新。
- **修复**：`HandleRotate()` 中主动刷新 ghost 尺寸和 `SetConnectors()`。
- **沉淀**：拖拽态是临时表现态，不能完全依赖全量重绘。

## 六、面试问答

**Q1：你为什么把 bool Rotated 改成 RotationState？**  
> 因为 bool 只能表达“是否旋转”，适合 1x2 变 2x1 这种宽高互换，但邻接接口需要知道 0°、90°、180°、270° 的具体方向。四状态能同时服务宽高、接口显示和邻接规则。

**Q2：LocalConnectableSides 和 GetWorldConnectableSides 有什么区别？**  
> `LocalConnectableSides` 是物品原始朝向下的接口配置，来自静态掉落数据；`GetWorldConnectableSides()` 是根据当前 `RotationState` 换算出的实际背包方向。UI 和邻接扫描都应该读世界方向。

**Q3：为什么规则表里的 SideA 不能直接和扫描到的 sideA 比？**  
> 规则表里的 `SideA` 是本地方向，扫描到的 `sideA` 是世界方向。物品旋转后，本地 Down 可能变成世界 Left。如果直接比较，就会导致旋转后的有效邻接无法触发。

**Q4：为什么 TryMatchNeighbor 要做正向和反向匹配？**  
> `ScanAdjacency()` 为了去重只扫描右边和下边，所以扫描到的 `itemA` 不一定是规则表里的 `TagA`。例如规则写 Rifle + Magazine，但实际摆放可能是 Magazine 在左、Rifle 在右。正反向匹配可以让规则不依赖摆放顺序。

**Q5：正反向匹配最容易错在哪里？**  
> 最容易把 Tag 和 Side 拆散。正确做法是 `rule.TagA` 对哪个 item，`rule.SideA` 就必须也由那个 item 转世界方向；`rule.TagB / SideB` 同理。不能只判断“标签在这两个物品里，边也在这两条边里”。

**Q6：为什么 AdjacencyEffect 记录世界边而不是本地边？**  
> `AdjacencyEffect` 是运行时结果，UI 金边和战斗效果关心的是当前哪条世界边生效。记录世界边可以让表现层直接使用，不需要再理解规则表和旋转状态。

**Q7：为什么丢弃后恢复原始朝向？**  
> 当前 `LootEntry` 没有保存运行时旋转状态。如果丢弃时写当前尺寸但保留本地接口，会生成混合错误数据。Demo 阶段选择恢复原始朝向，保证数据自洽；正式版可用 RuntimeDropData 保存旋转态。

## 七、习惯清单

1. 当规则涉及方向时，先区分本地方向和世界方向。
2. 状态表达要跟需求复杂度匹配，bool 不够就升级枚举。
3. UI、扫描、战斗效果要共用同一个方向事实源。
4. 临时修改入参的函数，失败时必须恢复调用前状态。
5. 规则匹配要保持字段归属，不要把 Tag 和 Side 拆散。
6. 正反向匹配用两个 bool 写清楚，不要写嵌套 if 迷宫。
7. 运行时效果对象应记录运行时世界结果，而不是静态配置方向。
8. 拖拽态表现要主动刷新，不能完全依赖 Redraw。
9. 静态掉落数据不要混入运行时旋转状态。

## 八、思考题（附复习参考）

**Q1：如果以后允许地面物品保留旋转状态，应该怎么设计？**  
> 不应该把旋转状态塞进静态 `LootEntry`。更合适的是新增运行时掉落数据，例如 `DropRuntimeData`，保存 `ItemId / Level / RotationState / BaseValue` 等运行时信息。

**Q2：如果规则表允许 `Up | Right` 这种多边集合，当前匹配要怎么改？**  
> 现在用 `GetWorldSides(rule.SideA) == sideA`，适合单边规则。如果规则允许多边集合，要改成包含判断：`(item.GetWorldSides(rule.SideA) & sideA) != 0`。

**Q3：为什么 ScanAdjacency 不扫描四个方向？**  
> 只扫右边和下边可以天然减少重复。同一对物品只会被扫描一次，规则顺序问题交给正反向匹配解决，而不是靠四向扫描制造更多重复结果。

**Q4：如果一个物品旋转 180°，宽高为什么不变但接口会变？**  
> 宽高是矩形占格尺寸，180° 后占格不变；接口是方向语义，Up 会变 Down、Left 会变 Right。所以宽高不变不代表方向不变。

**Q5：为什么拖拽中 activeSides 给 None？**  
> 手持物品已经离开背包数据层，不参与真实邻接扫描。拖拽中只展示“它有哪些接口”，不展示“它已经触发什么效果”，避免假金边误导玩家。
