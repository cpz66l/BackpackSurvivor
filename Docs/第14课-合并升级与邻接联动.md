## 一、这节课实现了什么

### 任务 1 · 合并升级（同名同级 2→1）

- `InventoryGrid` 增加 `CanMerge(source, target)`：只判断规则，不改状态。
- `TryMerge(source, target)` 负责真正执行：目标物品升级，来源物品从背包移除。
- `InventoryUIController.EndDrag` 接入合并分支：拖拽落点不能放置时，优先尝试和目标格物品合并。
- `ItemView.Bind` 显示 `Lv.x`，让玩家能看到合并结果。
- 合并规则暂定：同 `Id`、同 `Level`、不同实例、目标未到 `MaxLevel`。

### 任务 2 · 物品构筑标签

- `ItemTag` 作为物品类别标签：`Pistol / Rifle / Shotgun / SniperRifle / Magazine / Scope / FireCore / Armor / Medical`。
- `Item` 增加 `Tag` 和 `LocalConnectableSides`，普通物品默认 `None`，特殊物品用新构造函数注入。
- 手枪当前临时配置为 `ItemTag.Pistol`，可连接边为 `Left | Right`。
- 这一层仍在 `BS.Inventory` 纯数据程序集里，不依赖 `UnityEngine`。

### 任务 3 · 方向受限邻接规则

- `ConnectableSides` 用 `[Flags]` bitmask 表达上下左右接口。
- `AdjacencyRule` 表达规则：A 标签 + A 接触边 + B 标签 + B 接触边 → 效果。
- `AdjacencyEffectId` 用枚举表达效果 ID，避免字符串拼写事故。
- `AdjacencyEffect` 表达一次扫描命中的候选效果：效果 ID、双方物品、双方触发边。
- 第一条规则：手枪右边接手枪左边，或手枪左边接手枪右边 → `DualWield` 候选效果。

### 任务 4 · 邻接扫描

- `InventoryGrid.ScanAdjacency(rules)` 扫描全背包，只检查右边和下边，避免天然重复。
- `TryMatchNeighbor` 做五层守卫：空格、自身、接口边、规则表、去重 key。
- 同一个物品占多格时，通过 `itemA == itemB` 跳过自身邻接。
- 去重 key 用双方实例 hash 排序 + `EffectId`，避免同一对物品重复触发。
- 扫描层只返回“候选邻接效果”，不决定战斗是否真的生效。

### 任务 5 · 接口点 UI 表现

- `ItemView` 增加四个接口点 Image：上、右、下、左。
- `SetConnectors(visibleSides, activeSides)`：不可连接边隐藏，可连接未触发边显示灰色，已触发边显示金色。
- `InventoryUIController.Redraw` 每次重绘先扫描邻接效果，再把每个物品的可连接边和激活边投影给 `ItemView`。
- `GetActiveSides` 使用 bitmask 累加，支持一个物品未来同时被多个芯片/邻接效果影响。

## 二、最终代码（关键片段）

### 合并规则：判断和执行分离

```csharp
public bool CanMerge(Item source, Item target)
{
    if (source == null || target == null) return false;
    if (source == target) return false;
    if (source.Id != target.Id) return false;
    if (source.Level != target.Level) return false;
    if (target.Level >= target.MaxLevel) return false;

    return true;
}

public bool TryMerge(Item source, Item target)
{
    if (!CanMerge(source, target)) return false;
    target.IncreaseLevel();
    Remove(source);
    return true;
}
```

### 物品接口：标签 + 可连接边

```csharp
public ItemTag Tag { get; }
public ConnectableSides LocalConnectableSides { get; }

public Item(string id, Rarity rarity, int width, int height,
    ItemTag itemTag, ConnectableSides connectableSides)
{
    Id = id;
    baseWidth = width;
    baseHeight = height;
    Rarity = rarity;
    Rotated = false;
    Level = 1;
    MaxLevel = 3;
    Tag = itemTag;
    LocalConnectableSides = connectableSides;
}

public ConnectableSides GetWorldConnectableSides()
{
    return LocalConnectableSides;
}
```

### 邻接规则：不用 if-else 写死组合

```csharp
public class AdjacencyRule
{
    public ItemTag TagA { get; }
    public ConnectableSides SideA { get; }
    public ItemTag TagB { get; }
    public ConnectableSides SideB { get; }
    public AdjacencyEffectId EffectId { get; }
}
```

### 邻接扫描：只看右和下，避免重复

```csharp
for (int y = 0; y < Height; y++)
{
    for (int x = 0; x < Width; x++)
    {
        Item item = cells[x, y];
        if (item == null) continue;

        TryMatchNeighbor(x, y, x + 1, y,
            ConnectableSides.Right, ConnectableSides.Left,
            rules, effects, triggeredKeys);

        TryMatchNeighbor(x, y, x, y + 1,
            ConnectableSides.Down, ConnectableSides.Up,
            rules, effects, triggeredKeys);
    }
}
```

### UI 激活边：累加而不是覆盖

```csharp
private ConnectableSides GetActiveSides(Item item, List<AdjacencyEffect> effects)
{
    ConnectableSides activeSides = ConnectableSides.None;
    foreach (var effect in effects)
    {
        if (effect.ItemA == item)
            activeSides |= effect.SideA;
        if (effect.ItemB == item)
            activeSides |= effect.SideB;
    }
    return activeSides;
}
```

### 接口点表现：隐藏 / 灰色 / 金色

```csharp
private void SetConnector(Image connector,
    ConnectableSides side,
    ConnectableSides visibleSides,
    ConnectableSides activeSides)
{
    if ((visibleSides & side) == 0)
    {
        connector.gameObject.SetActive(false);
        return;
    }

    connector.gameObject.SetActive(true);
    connector.color = (activeSides & side) != 0
        ? new Color(1f, 0.78f, 0.15f, 1f)
        : new Color(0.55f, 0.55f, 0.55f, 0.9f);
}
```

## 三、周期链路

### 合并升级链路

```text
拖起物品
  → BeginDrag：grid.Remove(source)，ghost 跟随鼠标
  → 拖到已有物品格子上
  → Dragging：CanPlaceAt=false，但 CanMerge(source,target)=true → 预览为合法
  → EndDrag：当前位置不可放置 → 取 targetItem → TryMerge(source,target)
  → target.IncreaseLevel()
  → Remove(source)
  → OnChanged → Redraw
  → 背包只剩目标物品，标签显示 Lv.+1
```

### 邻接扫描链路

```text
背包发生变化 → Redraw
  → grid.ScanAdjacency(adjacencyRules)
  → 遍历格子，只检查右邻居和下邻居
  → 排除空格 / 同一物品自身 / 没有接口边
  → 用标签 + 接触边匹配规则表
  → 命中则生成 AdjacencyEffect 候选效果
  → 返回 effects 给表现层
```

### 接口点表现链路

```text
Redraw 生成 ItemView
  → visibleSides = item.GetWorldConnectableSides()
  → activeSides = GetActiveSides(item, effects)
  → ItemView.SetConnectors(visibleSides, activeSides)
  → 无接口边：隐藏
  → 有接口但未触发：灰色
  → 有接口且已触发：金色
```

### 后续真实生效链路（挂账，不在本课做）

```text
ScanAdjacency 返回候选效果
  → AdjacencyEffectResolver 结算候选效果
  → 按效果类型应用策略：唯一 / 可叠加 / 互斥 / 上限
  → DualWield：每把武器最多参与 1 组
  → 输出 ResolvedEffects
  → UI 显示真正生效边
  → 战斗系统读取真正生效效果
```

## 四、设计思考（这节课真正学的东西）

### 1. 判断和执行要拆开

`CanMerge` 只回答“能不能”，`TryMerge` 才真正改变世界。为什么这么拆？因为拖拽预览、实际松手、以后 AI/自动整理都会问同一个问题。如果判断逻辑写在执行里，UI 预览就只能偷偷复制一份规则，迟早分叉。**能不能是一种查询，做不做是一种命令；两者职责不同。**

### 2. 邻接不是四边万能

本课没有做“只要挨着就触发”。这是很关键的设计选择：背包构筑的乐趣来自形状、方向、标签共同限制。如果所有物品四边都能连，玩家只是在拼面积；如果接口边受限，玩家就在做空间规划。**限制不是削弱自由，限制是在制造可思考的选择。**

### 3. 扫描层只产出候选，不替玩法裁决

三把手枪横排时，扫描层可以发现两条候选 DualWield：A-B 和 B-C。这不代表玩法要允许三持。扫描层的职责是诚实报告“几何和规则表命中了什么”；玩法层的职责才是裁决“哪些真的生效”。这条边界立住后，后面做双持限制、芯片叠加、元素互斥都不会污染网格底层。

### 4. UI 要支持多邻接，但效果可以限制

`GetActiveSides` 用 `|=` 累加是正确方向。表现层应该有能力同时显示多个激活边，因为未来弹鼓、瞄准镜、火焰核心、护甲模块都可能从不同方向影响同一件装备。至于 DualWield 是否只能一组，那是结算器的规则，不应该靠 UI 覆盖某一边来“假装限制”。**表现能力要足，玩法限制要清。**

### 5. bitmask 是小系统的好武器

`ConnectableSides` 用 `[Flags]`，让“左+右”“上+下”“全部边”都能用一个字段表达。判断也很干净：`(sides & side) != 0`。当状态集合固定、小而频繁判断时，bitmask 比多个 bool 更集中，也比 List 更轻。

### 6. 临时硬编码可以存在，但要被看见

手枪标签和左右接口现在临时写在 `CreateItemFromLootEntry`，邻接规则临时写在 `InventoryUIController`。这在教学阶段可以接受，因为我们先验证玩法闭环。但它们必须被挂账：后续要迁到物品定义和规则配置里。临时方案最大的问题不是“脏”，而是“忘了它是临时的”。

## 五、踩坑记录

| 坑 | 根因 | 修法 | 沉淀 |
|---|---|---|---|
| TryMerge 消耗 source 的时机 | 合并后如果只升级 target，不移除 source，背包会留下两个物品实例 | `target.IncreaseLevel()` 后 `Remove(source)` | 合并是“来源消耗 + 目标成长”，不是单纯改数字 |
| activeSides 覆盖问题 | `activeSides = effect.SideA` 会让后命中的边覆盖前面的边 | 改为 `activeSides |= effect.SideA/SideB` | UI 投影层要支持多邻接；玩法限制放到结算层 |
| 三把手枪横排的歧义 | 扫描层会发现 A-B、B-C 两条候选 DualWield | 挂到第 16 课做结算器，规定每把武器最多参与 1 组 DualWield | 候选效果不等于真实生效效果 |
| 规则表临时放在表现控制器 | 第 14 课先验证表现，规则暂时靠 controller 内部 List | 第 18 课迁到静态配置/定义表 | 表现层不该长期拥有玩法规则 |
| 手枪标签临时写在收货口 | LootEntry 目前没有物品定义引用，先用 id 特判注入标签和接口边 | 第 18 课做 ItemDefinition / RuleDefinition | 数据驱动前，可以先硬编码验证，但必须清楚退出路线 |
| 接口方向暂不随旋转变换 | `GetWorldConnectableSides()` 当前直接返回 local sides | 第 18 课统一定规矩：接口是随物品旋转，还是固定在世界方向 | “Local/World” 命名已经预留了未来演进点 |

## 六、面试问答

**Q：为什么合并要有 `CanMerge` 和 `TryMerge` 两个方法？**
A：因为 UI 预览和实际执行都需要同一套规则。`CanMerge` 是查询，不产生副作用；`TryMerge` 是命令，会改变背包状态。拆开后，拖拽预览可以安全调用 `CanMerge`，松手时再调用 `TryMerge`。这避免了“为了预览复制一份规则”的分叉风险。

**Q：为什么邻接规则不用 if-else 写在扫描里？**
A：if-else 会让每新增一种构筑效果都改扫描器，扫描器会变成玩法规则垃圾桶。规则表把“怎么扫描”和“什么组合生效”分开：扫描器只负责几何、方向、标签匹配；内容扩展靠新增规则。这样更符合开闭原则。

**Q：为什么 `ConnectableSides` 用 `[Flags]`？**
A：因为方向集合固定且很小，上下左右天然适合 bitmask。一个字段就能表达 `Left | Right`，判断也只是按位与。比四个 bool 更集中，比 List/HashSet 更轻，尤其适合频繁扫描的网格系统。

**Q：三把手枪横排时，中间手枪两边都亮，算不算三持 bug？**
A：不直接算。那说明扫描层发现了两个候选 DualWield。真正是否允许三持，要由后续“邻接效果结算器”决定。本项目设计定为：DualWield 每把武器最多参与 1 组，所以第 16 课会把两条候选裁决成一条真正生效效果。

**Q：为什么 UI 要允许多边高亮？**
A：因为未来并不只有 DualWield。比如一把自动步枪右边接弹鼓、上边接瞄准镜、下边接火焰核心，这些都可能是合法多邻接。UI 层应该具备表达多个激活边的能力；具体哪些能叠加、哪些互斥，交给效果结算层。

**Q：为什么说 `ScanAdjacency` 返回的是候选效果？**
A：因为扫描只能证明“物品 A 和物品 B 在几何、标签、方向上命中了某条规则”，不能证明“玩法最终允许它生效”。例如双持唯一性、芯片叠加上限、元素互斥，都不是网格扫描该关心的事。候选和生效分开，是为了让底层保持纯净。

**Q：接口方向为什么分 Local 和 World？**
A：Local 是物品自己的接口定义，World 是放进背包并考虑旋转后的真实接口方向。本课 `GetWorldConnectableSides()` 暂时直接返回 local，是因为先验证邻接系统主链路。后面若决定接口随旋转移动，就只需要在这个函数里做方向变换，下游扫描不用大改。

## 七、习惯清单

1. 查询方法不改状态，执行方法才改状态；`CanXxx` / `TryXxx` 语义要诚实
2. 规则扩展优先用表驱动，不把玩法组合写成 if-else 长串
3. bitmask 字段写完要配套掌握 `|`、`&`、`|=` 三件套
4. UI 投影层负责“显示结果”，不要替玩法层“裁决规则”
5. 临时硬编码要留退出路线，并写进挂账清单
6. 命名里出现 `Local/World` 时，要明确当前是否真的做了空间转换
7. 扫描器只做扫描，结算器只做裁决，战斗系统只消费结果
8. commit 前继续跑 using 闸，尤其防 `UnityEditor.*` 混入运行时代码

## 八、思考题（附复习参考）

**Q1：为什么 `ScanAdjacency` 只检查右边和下边，不检查四个方向？**
> 因为全格扫描时，每对相邻物品会被访问两次。如果同时检查左右上下，A 的右边是 B，B 的左边又是 A，会天然重复。只检查右和下，可以覆盖所有水平/垂直邻接对，同时避免重复扫描。方向相反的规则通过规则表补一条镜像规则解决。

**Q2：如果一个物品占 2×2，为什么扫描时会碰到自己？怎么避免？**
> 背包格子里存的是物品引用，同一个 2×2 物品会占多个格子。扫描某个格子的右/下邻居时，邻居可能还是同一个物品实例。用 `if (itemA == itemB) return;` 跳过即可。这里比较引用是对的，因为我们要排除“同一个实例的不同占格”。

**Q3：`activeSides |= effect.SideA` 和 `activeSides = effect.SideA` 的区别是什么？**
> `=` 是覆盖，后一次命中会抹掉前一次命中的边；`|=` 是累加，把多个方向合并进同一个 bitmask。未来一个物品可能同时被多个邻接效果影响，所以 UI 投影必须用累加。是否允许这些效果同时生效，是结算器的职责。

**Q4：三把手枪横排时，为什么不直接在 `ScanAdjacency` 里阻止第二条 DualWield？**
> 因为那会把玩法裁决塞进扫描器。扫描器应该诚实返回候选事实：A-B 命中、B-C 也命中。至于 DualWield 是否一把枪只能参与一次，是效果策略，不是网格几何规则。放到结算器里，未来不同效果就能有不同策略：双持唯一、芯片可叠加、元素互斥。

**Q5：为什么临时规则表放在 `InventoryUIController` 里不是长期方案？**
> `InventoryUIController` 是表现层，它应该负责把数据画出来，而不是拥有玩法规则。短期放这里是为了快速验证接口点显示；长期应迁到数据定义或配置表，让数据层/规则层输出结果，表现层只消费结果。

**Q6：如果以后接口方向随旋转变化，应该改哪里最合理？**
> 优先改 `Item.GetWorldConnectableSides()`。`LocalConnectableSides` 保留物品原始方向接口，`GetWorld...` 根据 `Rotated` 把 Up/Right/Down/Left 做方向变换。这样 `ScanAdjacency` 仍然只问“世界方向上有没有接口”，不需要知道旋转细节。
