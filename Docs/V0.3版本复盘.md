## 一、交付结论

**V0.3 阶段目标达成：项目从“完整可试玩”推进到“具备内容扩展、反馈包装和局外记录”的版本。**

## 三、系统扩展复盘

### 1. 升级候选池

V0.2 的升级系统只有少量固定选项，能支撑原型，但不足以形成多局变化。V0.3 将升级拆成定义、生成和消费三层：

```text
LevelUpOptionDefinition：稳定 ID、分类、标题、描述、数值、权重、等级门槛、最大选择次数
LevelUpOptionGenerator：按等级和次数筛选，再按权重抽取，同轮去重
PlayerRunStats：统一承接升级结果，并提供各系统消费出口
```

这让升级不再只是 UI 弹窗，而是能真实影响伤害、射速、暴击、生命、减伤、移动、拾取、经验、金币和武器上限等运行期属性。

### 2. 邻接与背包构筑

V0.3 没有继续把每种邻接效果塞进 `BackpackWeaponActivator`，而是新增汇总层：

```text
InventoryGrid.ScanAdjacency
  -> AdjacencyEffectResolver 筛出有效效果
  -> BackpackEffectCollector 汇总数值 modifier
  -> Activator / 武器 / 被动系统消费
```

这样 `DualWield` 作为激活类效果保留特殊处理，攻速、伤害、暴击等数值类效果进入 modifier 汇总，机械臂、护甲和磁吸核心作为背包被动生效。这个拆法让后续新增效果时不用不断扩大同一个主流程脚本。

### 3. 内容池和价值

V0.3 将新增规则回填到真实内容池：机械臂、磁吸核心、护甲、瞄准镜、高价值收集品和传说物进入掉落与宝箱体系。

图标解析也从 `ItemTag` 粗粒度绑定升级为 `Item.Id` 优先、`ItemTag` 兜底。这样同样是收集品或武器，也可以按具体物品显示不同图标，避免内容增加后全部挤在同一套表现模板里。

价值体系按普通、不凡、稀有、史诗、传说拉开阶梯，让玩家摸到高品质物品时有明显收益感，也给结算和本地纪录提供可量化目标。

### 4. 音频与设置

音频从“几个字段播放 clip”升级为 Cue 表驱动：

```text
SfxId / WeaponSfxId
  -> AudioCue / WeaponAudioCue
  -> SfxPlayer.PlaySfx / PlayWeaponShoot
```

这样三种武器能使用不同音色，高频射击可以加冷却、音量、pitch 随机和多 clip 随机，降低后期听觉疲劳。

设置系统则形成了数据、服务和 UI 三层：

```text
GameSettings：音量、分辨率、窗口模式
SettingsService：Load / Save / Apply
SettingsPanelView：Slider / Dropdown 映射
```

设置用 `PlayerPrefs` 保存，音量和窗口/分辨率在 Build 中实测可以生效。第一版没有引入完整 AudioMixer，是一个符合 Demo 阶段成本的选择。

### 5. 敌人移动和远程敌人

V0.2 的敌人主要是直线追击，数量上来后容易重叠、卡障碍或摇摆。V0.3 将移动从 `EnemyAI` 拆出为 `EnemyMovement`，加入：

- 追玩家方向。
- 敌人之间的分离力。
- 障碍避让。
- 方向低频错峰采样。
- 实际移动方向平滑。
- 绕行方向记忆。

当前地图是开放竞技场，因此轻量 steering 比全员 NavMeshAgent 更符合成本收益。后续如果地图复杂度提高，再评估 NavMesh、Flow Field 或导航点系统。

远程敌人复用了既有 `Health`、掉落、投射物和对象池链路，通过保持距离、冷却射击和敌方子弹给中后期战斗增加走位压力。这个选择比提前做 Boss 更适合当前版本，因为它复用系统多、范围可控、对 15 分钟循环影响更均匀。

### 6. 本地存档与纪录

V0.3 的存档没有做断点续玩，而是做战绩留存：

```text
totalRuns
totalWins
bestBackpackValue
totalGold
legendaryFoundCount
legendaryCollectedValue
lastPlayedVersion
```

开局即记录总局数，胜利才累计胜场、局外金币和传说带出数据。这样失败和胜利的统计口径清晰，也避免把本地存档做成复杂局内状态快照。

## 四、架构沉淀

### 1. 先扩展消费链，再扩内容

V0.3 的升级、邻接和被动效果都遵循同一条原则：新增内容前先确认谁消费它。

```text
升级项 -> PlayerRunStats -> 武器/移动/拾取/经验/金币/生命消费
邻接项 -> EffectResolver/Collector -> 武器 modifier 消费
被动物品 -> BackpackPassiveCollector -> 全局 modifier 消费
```

这能避免“UI 上能选，但游戏里没效果”的假内容。

### 2. 保持主干稳定，增量加适配层

V0.3 没有推倒 V0.2 的主干系统，而是在既有链路旁边补适配层：

- `BackpackEffectCollector` 承接邻接数值汇总。
- `EnemyMovement` 承接移动执行。
- `SettingsService` 承接设置持久化和应用。
- `SaveService` 承接局外纪录保存。
- `ProjectilePoolProvider` 承接 prefab 与场景池引用问题。

这符合个人项目迭代中的一个重要工程原则：先保护已经跑通的闭环，再在边界上扩展能力。

### 3. 低成本方案也要有升级路线

V0.3 中有几处明确的“先不过度工程化”：

- 升级候选池先用代码定义表，而不是立刻完整 ScriptableObject 编辑器化。
- 设置先用 `PlayerPrefs`，不做复杂配置文件和多档位画质。
- 本地存档先用 JSON，不做账号、云存档和防篡改。
- 敌人移动先用局部 steering，不做全员 NavMesh。

这些选择不是“偷懒”，而是 Demo 阶段的性价比判断。关键是每个选择都保留了后续升级方向。

## 五、关键问题与修正

| 类型 | 问题 | 根因 | 处理 |
| --- | --- | --- | --- |
| 升级生成 | 首次升级能抽到 2 级选项 | 玩家开局就是 1 级，第一次升级后等级为 2 | 明确 `MinLevel` 语义，保留该行为 |
| 武器激活 | 双持奖励可能占基础激活位 | 基础激活和奖励激活顺序混在一起 | 调整为基础武器激活后再结算双持奖励 |
| 音频按钮 | 开始游戏偶发无反应 | 等待点击音协程延迟加载场景 | 改为立即加载，点击音用跨场景临时音源播放 |
| 设置 UI | 分辨率/窗口索引理解成本高 | Dropdown 索引和候选列表映射不直观 | 用候选列表集中生成，再用索引读取对应项 |
| 敌人移动 | 敌群抖动和避障摇摆 | 每次避让方向频繁左右切换 | 增加方向平滑和绕行方向记忆 |
| 存档服务 | MainMenu UI 被带进 Run 场景 | `SaveService` 挂在 Canvas 上并 DontDestroyOnLoad | 改为独立根对象承载跨场景服务 |
| 弹窗点击 | 设置/纪录面板外仍能点到后方按钮 | UI 没有遮挡点击穿透 | 增加全屏遮罩或阻挡层 |

这些问题的共同点是：大部分不是算法难题，而是 Unity 项目中常见的生命周期、引用边界、UI 射线和跨场景对象管理问题。

## 六、性能与发布验证

V0.3 发布前做了 Editor Profiler 快扫和 Build 实测。快扫中能看到部分尖刺，但主要落在：

- `EarlyUpdate.UpdatePreloading / Loading.UpdatePreloading`。
- `Gfx.CreateTexture / Gfx.UploadTexture`。
- `WaitForLastPresentationAndUpdateTime / WaitForGPU`。
- Editor/Profiler 观察环境本身带来的开销。

同时，多数普通帧中 `PlayerLoop` 很低，用户在正式 Build 中完整试玩后反馈没有明显卡顿，战斗节奏和数值压力也没有明显缺陷。

因此本阶段没有在发布前做大规模性能重构，而是选择记录证据、保留观察项。这个决策延续了 V0.2 的原则：**性能优化先判断瓶颈属于哪里，再决定是否改代码。**

## 七、玩家体验复盘

V0.3 对体验提升最大的不是单个系统，而是几个系统叠加后形成的新张力：

- 升级候选池变宽后，每局成长路线更不固定。
- 机械臂、磁吸核心、护甲、瞄准镜让背包不只是武器和芯片格子。
- 远程敌人让玩家整理背包和追宝箱时仍要观察战场。
- 音效、BGM、设置菜单和纪录面板让 Demo 更像一个可交付游戏。
- 本地纪录让玩家有“下一局能不能带出更高价值”的局外目标。

当前仍有不足：构筑收益集中展示不够，金币还没有消费出口，传说物图鉴还没做，远程敌人类型也只有第一版。但对于 v0.3 的目标来说，系统面已经铺开，后续可以继续纵向加深。

## 八、版本不足与风险

1. **内容仍然是 Demo 量级**：升级、芯片和敌人类型已经扩展，但距离完整商业内容仍有差距。
2. **配置数据化还不彻底**：部分内容仍在代码表或场景字段中维护，数量继续增长后需要 ScriptableObject 化。
3. **存档缺少迁移策略**：当前已有版本字段，但字段结构变化时还需要正式迁移逻辑。
4. **音频没有完整混音管线**：当前设置可用，但 AudioMixer、低血量提示、命中音色层次还可以继续补。
5. **敌人移动仍是开放地图方案**：复杂关卡、长墙、封闭区域需要重新评估导航体系。
6. **资源授权仍需谨慎**：公开展示可以保留 Demo 素材，但商业化或继续传播前需要逐项确认授权。

## 九、下一阶段方向

V0.3 之后建议不要立刻追求 Boss 或大而全系统，而是围绕“内容深度和作品表达”继续推进：

```text
P0：补更多高性价比升级项、芯片和背包被动物品
P1：做构筑收益展示，让玩家知道当前总收益
P1：给局外金币增加消费出口，形成更明确的长期目标
P2：补第二种远程敌人或特殊敌人，增强中后期压力变化
P2：完善音频混音、命中反馈和低血量提示
P3：再评估 Boss、复杂关卡、完整数据化和更重的导航方案
```

如果把 V0.2 看作“第一版完整作品”，那么 V0.3 的价值是证明这个作品不是一次性原型，而是可以沿着已有架构继续扩内容、扩反馈、扩敌人行为和扩局外记录。

## 十、阶段总结

V0.3 的核心价值可以概括为一句话：

> 在不推倒 V0.2 主干的前提下，把《背包幸存者》扩展成一个更有构筑深度、更有战斗变化、更像正式 Demo 的版本。

这个阶段的成长点不是“写了多少新脚本”，而是建立了更清晰的扩展方法：

```text
先确认玩家体验目标
  -> 再补系统承载层
  -> 再把内容接入真实掉落和消费侧
  -> 再通过设置、音频、存档和 Build 验收完成交付闭环
```

对求职展示来说，V0.3 能体现的能力不只是 Unity API 使用，而是从玩法、架构、内容、性能验证到发布包装的完整工程推进能力。
